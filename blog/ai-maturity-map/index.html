AI 도입 성숙도 맵: Skill, MCP, Plugin, AI Ops — 내가 지금 알아야 할 개념은 어디까지인가

AIAI OpsMCPPrompt Engineering실무자동화

AI를 쓰다 보면 어느 순간부터 용어가 쏟아지기 시작해요. Prompt Engineering은 어느 정도 감이 오는데, MCP가 나오고, Skill이 나오고, Plugin이 나오고, Marketplace가 나오고, AI Ops가 나와요. 각각 설명을 읽어보면 다 비슷한 것 같기도 하고, 뭔가 다른 것 같기도 하죠.

가장 당황스러웠던 건 “지금 내가 알아야 하는 건지”를 판단하기 어렵다는 거였어요. Prompt Engineering 단계에서 AI Ops를 공부하는 건 집도 없는데 인테리어 걱정하는 것과 비슷해요. 반대로 프로덕션을 운영하는데 Prompt Engineering만 알고 있으면 무너지기 시작하죠.

이 글은 AI 도입 성숙도 레벨별로 어떤 개념이 왜 등장하는지, 각 단계에서 어떤 실수를 자주 하는지를 정리해요. 목차에서 “지금 내가 있는 레벨”을 찾아서 읽어도 돼요.

전체 지도: 5단계로 보는 성숙도

L5
AI Ops "프로덕션에서 AI가 지금도 잘 작동하고 있나?"
L4
Marketplace & Orchestration "여러 에이전트를 조합해서 쓸 수 있나?"
L3
Skill & Plugin "반복되는 작업을 표준화할 수 있나?"
L2
Tool Use & MCP "AI가 외부 시스템을 직접 쓸 수 있나?"
L1
Prompt Engineering "어떻게 하면 원하는 답을 일관되게 얻을 수 있나?"

레벨이 높다고 좋은 게 아니에요. 팀 규모, 서비스 복잡도, 사용량에 따라 어디서 멈추는 게 맞는지가 달라요. 지금 어떤 문제를 겪고 있는지가 더 중요한 기준이에요.

L1: Prompt Engineering — 기초이자 영원한 숙제

Prompt Engineering은 LLM에게 원하는 결과를 일관성 있게 뽑아내는 방법이에요. “잘 물어보는 것”처럼 들리지만, 실제로는 구조적인 기법들이 있어요.

가장 기본은 Zero-shot이에요. 별도 예시 없이 직접 요청하는 방식이라 빠르고 간단해요. 특정 형식이 필요한 경우라면 Few-shot이 효과적이에요. 원하는 출력 형식의 예시를 2-3개 보여주면, 모델이 그 패턴을 따라가요. 복잡한 추론이 필요할 땐 **Chain of Thought(CoT)**가 정확도를 올려줘요. “단계별로 생각해봐”라고 유도하는 방식이죠. 그리고 역할이나 맥락을 고정하고 싶을 땐 System Prompt를 써서 에이전트의 페르소나를 설정해요.

이 레벨에서 가장 큰 실수는 프롬프트를 코드처럼 관리하지 않는 거예요. 슬랙에 공유하거나 Notion에 적어두는 방식으로 관리하면, 모델이 업데이트될 때마다 결과가 달라지는데 왜 달라졌는지 추적이 안 돼요. 프롬프트는 코드예요. 버전 관리가 필요하고, 변경 이력이 남아야 하고, 테스트 케이스가 있어야 해요.

CoT를 모든 곳에 쓰는 것도 흔한 실수예요. Chain of Thought는 복잡한 추론에 효과적이지만 토큰을 2-4배 더 써요. Chain of Draft 연구에 따르면 CoT와 동일한 정확도를 7.6% 토큰만으로 달성할 수 있어요. 단순 분류나 요약 작업에 CoT를 쓰면 비용만 올라가요.

같은 프롬프트로 10번 돌렸을 때 결과가 일관적이고, 프롬프트에 버전이 붙어 있으면 L1을 충분히 활용하고 있는 거예요. AI가 외부 데이터나 시스템과 연결돼야 하는 순간, L2가 필요해져요.

L2: Tool Use & MCP — AI에게 손발을 붙이다

LLM 단독으로는 할 수 없는 일들이 있어요. 실시간 데이터 조회, 파일 읽기/쓰기, 외부 API 호출, 코드 실행 같은 것들이죠. 이 능력을 붙여주는 게 Tool Use이고, 그 연결 방식을 표준화한 프로토콜이 **MCP(Model Context Protocol)**예요.

Anthropic이 공개한 MCP는 AI 에이전트와 외부 도구 사이의 USB 인터페이스 같은 거예요. MCP 서버 하나를 붙이면 에이전트가 그 서버가 노출하는 함수(Tool), 데이터(Resource), 프롬프트 템플릿(Prompt)에 접근할 수 있어요. Slack 메시지 보내기, DB 조회, 파일 관리 같은 것들이 모두 MCP Tool로 노출될 수 있어요.

Red Hat의 2026년 분석이 MCP를 잘 표현해요. “MCP는 에이전트의 감각 기관이에요. 외부 세계와 연결하는 인터페이스죠.”

보안 범위를 명확히 잡지 않는 게 가장 흔한 실수예요. MCP로 DB에 접근을 허용할 때 “읽기 전용”인지 “쓰기 포함”인지 명확히 안 해두면, 에이전트가 예상치 못한 데이터를 수정하거나 삭제할 수 있어요. Tool Use를 붙일 때는 최소 권한 원칙이 필수예요. 에러 처리도 빠뜨리면 안 돼요. 외부 API가 타임아웃 나거나 응답 형식이 바뀌면 에이전트 전체가 멈춰요.

Tool이 붙기 시작하면 “이 패턴을 매번 프롬프트로 설명해야 하나?”라는 질문이 생겨요. 그게 L3으로 가는 계기예요.

L3: Skill & Plugin — 패턴을 재사용하다

Nevo Systems가 세 개념을 가장 명확하게 정리했어요.

Skills는 지식이고, Plugins는 패키지이고, MCP는 연결이에요.

Skill은 에이전트에게 “이런 상황에선 이렇게 행동해”를 가르치는 프롬프트 기반 지침이에요. 코드 없이 마크다운 파일로 작성하고, 에이전트의 절차적 기억(procedural memory)이라고 볼 수 있어요. “PR 설명 써줘”를 매번 컨벤션 설명하면서 요청하고 있다면, 그걸 Skill로 만들어두면 팀 전체가 같은 품질의 결과를 얻어요.

Plugin은 Skill, Hook, 서브에이전트, 설정을 하나로 묶은 배포 가능한 패키지예요. 팀 내에서 또는 외부에 공유할 수 있는 단위죠. 비유로 정리하면 MCP는 에이전트에게 연장을 쥐여주는 것, Skill은 매뉴얼을 알려주는 것, Plugin은 연장과 매뉴얼과 설정을 한 박스에 담아 배포하는 것이에요.

Skill은 구체적일수록 좋아요. “모든 글쓰기를 잘해주는 Skill”은 사실 아무것도 잘 못 해요. “기술 블로그 도입부 작성”, “버그 리포트 포맷팅”, “PR 체크리스트 검토”처럼 명확한 범위가 있어야 일관된 결과가 나와요. Plugin과 MCP를 혼용하는 것도 주의해야 해요. 외부 시스템 연결은 MCP, 행동 패턴화는 Skill, 배포 단위화는 Plugin이에요. 역할이 섞이면 하나가 바뀔 때 다른 게 영향을 받기 시작해요.

팀 규모가 커지고 에이전트가 여러 개가 되면 “어디서 무슨 Skill을 쓰는지”를 관리해야 하는 시점이 와요. 그게 L4예요.

L4: Marketplace & Orchestration — 에이전트를 조합하다

Marketplace는 Plugin이나 Skill을 발견하고 배포하는 생태계예요. 내부적으로는 팀이 만든 에이전트와 도구를 공유하는 카탈로그가 될 수도 있고, Claude.ai나 GPT Store처럼 외부 마켓이 될 수도 있어요.

Orchestration은 여러 에이전트가 협력해서 하나의 복잡한 작업을 처리하는 구조예요. 단일 에이전트에게 주문 조회, 환불 처리, 상품 추천을 모두 맡기면 복잡도가 폭발해요. 역할을 나눠서 오케스트레이터가 적절한 에이전트에게 위임하는 구조가 더 견고해요.

오케스트레이터 없이 에이전트들이 서로 직접 소통하게 두면 디버깅이 불가능해져요. 어디서 무슨 결정을 내렸는지 추적이 안 되거든요. 반드시 중앙 오케스트레이터가 흐름을 제어해야 해요. 외부 Marketplace에서 Plugin을 가져올 땐 어떤 Tool을 노출하는지, 어떤 데이터에 접근하는지 반드시 검토해야 해요. 에이전트의 행동 범위가 넓어지는 만큼 보안 리스크도 커지거든요.

시스템이 실제 프로덕션 트래픽을 받기 시작하면 새로운 질문이 생겨요. “지금도 잘 작동하고 있나?” 그게 L5예요.

L5: AI Ops — 프로덕션에서 살아남기

L5는 AI를 “운영”하는 영역이에요. 배포 후에도 에이전트가 잘 작동하는지, 비용은 어떻게 통제하는지, 문제가 생겼을 때 어떻게 감지하는지를 다뤄요.

모델 드리프트: AI가 조용히 나빠지는 현상

**모델 드리프트(Model Drift)**는 배포 시점에는 잘 작동하던 AI가 시간이 지나면서 점점 결과가 나빠지는 현상이에요. 갑자기 망가지는 게 아니라 서서히 품질이 떨어지기 때문에 눈치채기 어려워요.

원인은 크게 두 가지로 나뉘어요. 데이터 드리프트는 사용자 입력 패턴이 바뀌는 경우예요. 처음엔 “배송 언제 와요?”류의 단순 문의가 많았는데, 서비스가 성장하면서 “해외 직구 반품 프로세스 설명해줘”처럼 복잡한 문의가 늘어나면 같은 모델이 다르게 동작해요. 컨셉 드리프트는 세상이 바뀌는 경우예요. 작년 규정으로 학습한 모델이 올해 바뀐 법령을 모르거나, 경쟁사가 출시한 신제품을 모르는 식이에요.

Orq.ai의 2026년 가이드에 따르면 드리프트 감지에는 통계적 거리 측정(KL Divergence, PSI, KS Test)이 효과적이에요. 근데 LLM에서는 정량 지표보다 사용자 행동 신호가 먼저 나타나는 경우가 많아요.

드리프트가 시작될 때 나타나는 초기 신호들이에요.

  • 사용자가 같은 질문을 다시 입력하는 빈도가 늘어나요
  • 답변에 thumbs down 비율이 올라가요
  • 챗봇에서 사람 상담으로 에스컬레이션이 증가해요
  • 평균 대화 턴 수가 늘어나요 (한 번에 해결이 안 됨)

이 신호들을 먼저 포착하고, 이후 정량 지표로 확인하는 흐름이에요. 사용자 피드백 루프를 처음부터 설계해두는 이유가 여기 있어요.

비용 최적화: 프로덕션의 현실

개발 환경에서 잘 작동하던 에이전트가 프로덕션에서 트래픽을 받으면 비용이 선형으로 증가해요. 세 가지 축으로 접근하는 게 효과적이에요.

첫 번째는 모델 라우팅이에요. 모든 요청에 최고 성능 모델을 쓸 필요가 없어요. 분류, 요약, 키워드 추출 같은 단순 작업은 소형 모델로 충분해요. 복잡도 기반으로 라우팅하면 전체 비용을 40-60% 줄일 수 있어요.

두 번째는 캐싱이에요. Anthropic의 Prompt Caching은 동일한 시스템 프롬프트나 긴 문서를 캐시해서, 캐시 히트 시 입력 토큰 비용의 90%를 절감해요. 에이전트 워크플로우처럼 같은 컨텍스트를 반복 참조하는 패턴에서 특히 효과적이에요.

세 번째는 Batch 처리예요. 실시간이 필요 없는 작업은 Batch API를 써요. OpenAI, Anthropic 모두 비동기 Batch API에서 약 50% 할인을 제공해요. 야간 분석, 대량 문서 처리처럼 타이밍이 덜 중요한 작업에 적용하면 그 영역 비용이 절반으로 줄어요.

관찰 가능성: 블랙박스를 열다

AI Ops의 핵심은 에이전트가 왜 그런 결정을 내렸는지 설명할 수 있어야 한다는 거예요. 로그가 없으면 문제가 생겼을 때 원인을 찾을 수 없어요.

최소한 입력 프롬프트(버전 포함), 모델 응답, 토큰 수, 호출된 Tool과 결과, 응답 시간, 사용자 피드백은 기록해야 해요. Fiddler AI의 LLMOps 가이드는 드리프트 메트릭, 재학습 파이프라인, 크로스 팀 협업 채널이 함께 있어야 진짜 운영 체계라고 말해요.

L5에서 자주 하는 실수를 짚어볼게요. 모니터링 없이 배포하는 게 가장 흔해요. 배포 후에 뭘 볼 것인지, 알람을 어디에 걸 것인지가 없으면 드리프트를 몇 달 뒤에야 알게 돼요. 재학습 주기를 고정하는 것도 문제예요. “3개월마다 파인튜닝”처럼 정해두면, 외부 이벤트(트렌드 변화, 규정 변경, 신제품 출시)로 인한 드리프트를 적시에 잡지 못해요. 주기보다 신호 기반 트리거가 나아요. 그리고 비용 알람을 안 걸어두면, 루프에 빠진 에이전트가 조용히 수백만 원을 쓰고 있어도 모를 수 있어요.

내가 지금 어느 레벨인가

이 레벨들은 순서대로 밟아야 하는 건 아니에요. 서비스 성격에 따라 L2에서 멈추는 게 맞는 팀도 있고, L4부터 고민해야 하는 팀도 있어요. 지금 어떤 문제를 겪고 있는지에서 출발하면 어느 레벨이 필요한지 보여요.

"결과가 매번 달라요" → L1: Prompt Engineering 강화, 버전 관리 도입
"AI가 실시간 데이터를 못 가져와요" → L2: MCP / Tool Use 도입
"같은 작업을 매번 다시 설명해요" → L3: Skill 만들기, 반복 패턴 패키징
"에이전트가 많아져서 관리가 안 돼요" → L4: Orchestration 구조화, 내부 Marketplace 구축
"배포 후 뭔가 이상한데 원인을 모르겠어요" / "비용이 왜 이렇게 나왔는지..." → L5: 관찰 가능성 구축, 드리프트 모니터링, 비용 최적화

AI 용어들이 난무하는 건, 그 각각이 실제로 다른 문제를 해결하기 때문이에요. 지금 어떤 문제를 가지고 있는지를 알면, 어떤 개념이 필요한지도 따라와요.
