AI 에이전트의 기억 구조: 어제 대화를 기억하는 에이전트 만들기

AIAgentLLM메모리아키텍처실무

에이전트를 처음 만들고 나면 꽤 만족스러워요. 툴도 쓰고, 멀티스텝 추론도 하고, 원하는 결과를 잘 뽑아내죠. 그런데 며칠 지나면 한 가지 이상한 점이 보여요.

사용자가 어제 했던 이야기를 또 처음부터 설명하고 있어요. 에이전트가 모르거든요. 저번에 들은 게 없어요. 매 대화를 새로 시작해요. 어제 세 시간 동안 쌓은 컨텍스트도, 사용자가 설정한 선호도도, 이전에 실패했던 시도도 — 전부 사라져 있어요.

이 문제가 단순히 “히스토리를 저장하면 해결되는 것”이 아니에요. 에이전트의 기억은 구조가 다른 여러 레이어로 이루어져 있고, 어떤 정보를 어디에 어떻게 저장하느냐에 따라 에이전트의 성격 자체가 달라지거든요. 이 글은 그 구조를 설계하는 방법에 대한 이야기예요.

사람의 기억과 AI의 기억

사람의 기억 연구에서 나온 분류 체계가 있어요. 단기 기억(Working Memory), 장기 기억(Long-term Memory), 그리고 장기 기억 안에서도 사건 기억(Episodic), 지식 기억(Semantic), 절차 기억(Procedural)으로 나뉘어요.

CoALA(Cognitive Architectures for Language Agents) 논문은 이 인지과학 프레임워크를 AI 에이전트에 그대로 적용해요. 에이전트의 메모리도 같은 방식으로 설계할 수 있다는 주장이에요.

에이전트 메모리 유형

├── In-context Memory     (작업 기억 — 지금 당장 처리 중인 것)
├── Episodic Memory       (사건 기억 — 과거에 무슨 일이 있었는지)
├── Semantic Memory       (지식 기억 — 사실, 개념, 도메인 지식)
└── Procedural Memory     (절차 기억 — 어떻게 하는지, 어떤 도구가 있는지)

각각이 뭔지 구체적으로 볼게요.

In-context Memory: 지금 이 순간의 작업 공간

컨텍스트 윈도우가 바로 In-context Memory예요. 에이전트가 현재 보고 있는 모든 것 — 시스템 프롬프트, 대화 히스토리, 툴 결과, 현재 진행 중인 데이터 — 이 모두가 이 안에 있어요.

특징은 세 가지예요. 속도가 가장 빠르고, 추론이 바로 가능하고, 대화가 끝나면 사라져요.

# In-context Memory의 실제 모습
messages = [
    {"role": "system", "content": "너는 계약서 분석 전문가야..."},  # 고정 지시
    {"role": "user",   "content": "이 계약서 3조를 해석해줘"},      # 현재 요청
    {"role": "assistant", "content": "[툴 호출 결과]..."},          # 진행 중인 추론
    {"role": "user",   "content": "그럼 5조는?"},                   # 이어지는 대화
]

현재 최신 모델들의 컨텍스트 윈도우는 Claude Sonnet 4.6 이상과 Gemini 1.5 모두 1M 토큰까지 지원해요. 그래서 단기 대화나 단일 문서 처리는 컨텍스트만으로도 충분해요.

문제는 컨텍스트가 꽉 차거나 대화가 끊어지면 모든 게 사라진다는 거예요. 이걸 해결하는 게 나머지 메모리 레이어들이에요.

Episodic Memory: 지난 대화의 기록

“저번에 이런 걸 시도했다가 실패했어요”, “지난주에 A 사용자가 이런 피드백을 줬어요” — 이런 정보가 Episodic Memory예요. 사건의 기록이에요.

구현 방법은 크게 두 가지예요.

전체 저장 방식: 대화 전문을 DB에 저장하고, 관련 대화를 검색해서 컨텍스트에 포함시켜요.

import mem0

client = mem0.MemoryClient(api_key="...")

# 대화 후 자동 저장
client.add(messages, user_id="user_123")

# 다음 대화 시작 시 관련 기억 검색
relevant = client.search("계약서 해지 조항", user_id="user_123")

# 검색된 기억을 시스템 프롬프트에 포함
system_prompt = f"""
너는 계약서 분석 전문가야.

이 사용자와의 이전 대화 중 관련된 것:
{relevant}
"""

요약 저장 방식: 매 대화가 끝날 때 핵심 정보만 추출해서 저장해요. 컨텍스트 효율이 훨씬 좋아요.

# 대화 종료 시 요약 생성
summary_prompt = """
다음 대화에서 미래 대화에 유용할 정보만 추출해줘.
- 사용자의 역할/소속
- 설정된 선호도나 제약
- 완료된 작업과 결과
- 미해결 질문이나 다음 단계

[대화 내용]: {conversation}

JSON으로 반환해줘.
"""

요약 방식은 저장 비용과 검색 정확도 면에서 유리하지만, 요약 과정에서 정보가 손실될 수 있어요. 중요한 대화는 원문 보관, 일반적인 대화는 요약 — 이렇게 혼용하는 패턴이 실무에서 많이 쓰여요.

Semantic Memory: 에이전트가 아는 지식

도메인 지식, 사실 정보, 조직의 정책, 제품 스펙 — 이런 “알고 있어야 하는 것들”이 Semantic Memory예요.

이걸 모두 시스템 프롬프트에 넣을 수는 없어요. 토큰 한계가 있고, 매번 전체를 로드하는 건 비효율적이거든요. 그래서 RAG(Retrieval-Augmented Generation)가 Semantic Memory의 대표적인 구현 방법이에요.

사용자 질문 → 임베딩 → 벡터 DB 검색 → 관련 지식 추출 → 컨텍스트에 포함 → 응답

단순 RAG와 에이전트용 Semantic Memory의 차이는 에이전트가 스스로 무엇을 검색할지 결정한다는 거예요.

tools = [
    {
        "name": "search_knowledge_base",
        "description": "제품 문서, 정책, 기술 스펙을 검색해요. 사용자 질문에 답하기 전에 관련 문서가 있는지 먼저 확인하세요.",
        "input_schema": {
            "type": "object",
            "properties": {
                "query": {"type": "string", "description": "검색할 내용"},
                "category": {"type": "string", "enum": ["policy", "product", "technical"]}
            }
        }
    }
]

에이전트가 이 툴을 갖게 되면 질문이 들어올 때마다 관련 지식을 직접 찾아요. 지식이 바뀌어도 DB만 업데이트하면 돼요. 시스템 프롬프트를 수정할 필요가 없어요.

Procedural Memory: 어떻게 하는지에 대한 기억

“이런 상황에서는 이렇게 행동해야 한다” — 행동 패턴, 워크플로우, 사용 가능한 툴 목록이 Procedural Memory예요. 주로 시스템 프롬프트와 툴 정의로 구현돼요.

재미있는 건 이 메모리도 동적으로 바뀔 수 있다는 거예요. 정적인 시스템 프롬프트 하나로 모든 상황을 처리하는 것보다, 상황에 맞게 다른 절차를 로드하는 게 더 효과적이거든요.

# 사용자의 역할에 따라 다른 절차(Procedural Memory)를 로드
def get_system_prompt(user_role: str) -> str:
    base = "너는 계약서 분석 에이전트야."

    role_procedures = {
        "legal": "법적 위험을 최우선으로 식별하고, 모든 주장에 조항 번호를 명시해.",
        "sales": "계약 조건 중 협상 가능한 부분을 강조하고, 상업적 리스크 위주로 분석해.",
        "finance": "결제 조건, 페널티, 환불 조항을 우선 분석하고 수치로 요약해.",
    }

    return base + "\n\n" + role_procedures.get(user_role, "균형 있게 전체를 검토해.")

이렇게 하면 같은 에이전트가 법무팀에게는 법적 에이전트로, 영업팀에게는 영업 에이전트로 동작해요. Procedural Memory가 에이전트의 역할을 정의하는 거예요.

현재 기술은 이 문제를 어떻게 풀고 있나

이론은 알겠는데, 실제로 어떻게 구현하냐고요? 현재 가장 많이 쓰이는 도구들이 각 문제를 어떻게 접근하는지 볼게요.

mem0: 추출-통합-저장 3단계 파이프라인

mem0는 2025년 4월 arXiv에 발표된 논문(arXiv:2504.19413)과 함께 프로덕션 수준의 메모리 레이어로 자리잡았어요. 핵심은 대화를 단순히 저장하는 게 아니라 의미 있는 사실로 추출하고 기존 기억과 통합하는 거예요.

대화 입력 (최근 10개 메시지 + 롤링 요약)
         ↓
  [1단계: 추출]
  LLM이 기억할 만한 사실을 이산적인 자연어 문장으로 추출
  예: "사용자는 마케팅팀 소속", "월요일 오전 보고서 선호"
         ↓
  [2단계: 통합]
  각 후보 사실을 기존 기억과 벡터 유사도로 비교
  → ADD   (관련 기억 없음, 신규 저장)
  → UPDATE (기존 기억과 겹침, 보강)
  → DELETE (기존 기억과 모순, 교체)
  → NOOP  (이미 알고 있음, 스킵)
         ↓
  [3단계: 저장]
  벡터 DB (Qdrant, Pinecone 등 20개 백엔드 지원)
  + 그래프 변형(mem0g): Neo4j에 엔티티-관계 트리플렛으로 저장

벤치마크 결과가 인상적이에요. LOCOMO 데이터셋 기준으로 전체 컨텍스트 방식(26k 토큰)의 7분의 1 수준인 약 7k 토큰을 쓰면서도 정확도는 더 높아요. p95 검색 레이턴시가 0.2초로, 실시간 에이전트에 붙일 수 있는 수준이에요.

Zep/Graphiti: 시간을 기억하는 지식 그래프

Zep의 엔진인 Graphiti는 좀 다른 접근이에요. 벡터 DB 대신 Neo4j 지식 그래프를 쓰고, 각 사실에 타임스탬프를 네 개씩 붙여요.

사실 엣지의 구조:
  t'_created  — Graphiti가 이 사실을 저장한 시점
  t'_expired  — 이 사실이 무효화된 트랜잭션 시점
  t_valid     — 실제 세계에서 이 사실이 참이 된 시점
  t_invalid   — 실제 세계에서 이 사실이 거짓이 된 시점

이게 왜 필요하냐면, “2024년 3월 기준으로 이 계약의 상태는?”처럼 과거 시점을 기준으로 한 질문을 벡터 검색은 못 풀거든요. Graphiti는 이걸 그래프 쿼리로 해결해요.

모순이 발생하면 기존 사실을 삭제하지 않고 t_invalid 타임스탬프만 찍어요. 그러면 “이전에는 맞았지만 지금은 틀린 정보”를 구분할 수 있죠. LongMemEval 벤치마크에서 시간 추론 항목이 48.2% 향상된 게 이 구조 덕분이에요.

Letta: 컨텍스트를 OS처럼 관리하기

Letta(구 MemGPT)의 핵심 아이디어는 컨텍스트 윈도우를 RAM으로, 외부 저장소를 디스크로 보는 거예요. 그리고 무엇을 RAM에 올리고 내릴지를 에이전트 스스로 결정하게 해요.

# Letta 에이전트의 메모리 구조
# 에이전트는 아래 함수들을 직접 호출해서 메모리를 관리해요

# 핵심 메모리 (항상 컨텍스트에 로드)
core_memory_replace(name="human", old_content="...", new_content="...")

# 아카이브 메모리 (필요할 때만 로드)
archival_memory_insert(content="중요한 사실을 여기에 저장")
archival_memory_search(query="관련 정보 찾기")

# 회상 메모리 (과거 대화 검색)
conversation_search(query="이전에 이 주제로 얘기한 것")

일반 메모리 시스템과의 차이는 외부 ETL 작업이 아니라 에이전트의 결정으로 메모리가 관리된다는 거예요. “이 정보는 나중에 필요할 것 같다”는 판단을 에이전트가 직접 해요. 여러 에이전트가 같은 메모리 블록을 공유할 수도 있어서 멀티 에이전트 협업에 유리해요.

LangGraph: 대화 범위와 장기 저장의 분리

LangGraph는 메모리를 두 개의 분리된 프리미티브로 제공해요.

# Checkpointer — 같은 대화(thread) 안에서의 상태 유지
from langgraph.checkpoint.postgres import PostgresSaver

graph = graph.compile(checkpointer=PostgresSaver(conn))
# thread_id가 같으면 이전 상태에서 이어서 실행

# Store — 사용자/에이전트 간 장기 기억
from langgraph.store.postgres import PostgresStore

store = PostgresStore(conn)
store.put(
    namespace=("user_123", "memories"),
    key="preference_01",
    value={"content": "보고서는 항상 요약 먼저 달아줘"}
)

# 다른 대화, 다른 에이전트에서도 접근 가능
results = store.search(("user_123", "memories"), query="보고서 형식")

Checkpointer는 현재 대화의 진행 상태를 저장하고, Store는 사용자나 에이전트 단위의 장기 기억을 관리해요. LangMem SDK를 함께 쓰면 대화 종료 후 자동으로 기억을 추출해서 Store에 저장하는 파이프라인을 빠르게 구성할 수 있어요.

프로덕션 대화 라이프사이클

개념을 알았으면 실제 흐름을 볼게요. 메모리가 붙은 에이전트가 한 번의 대화를 처리하는 전체 사이클이에요.

═══════════════════ 세션 시작 ═══════════════════

① 사용자 프로필 로드 (Semantic Memory)
   → user_id로 핵심 사실 조회
   → 시스템 프롬프트 상단에 YAML 형식으로 주입
     예: role: 마케팅팀 / preference: 요약 먼저 / timezone: KST

② 관련 에피소드 검색 (Episodic Memory)
   → 현재 메시지로 벡터 + BM25 + 엔티티 복합 검색
   → relevance > 0.5, 24개월 이내 기억만 포함
   → 상위 K개를 컨텍스트에 내러티브 형식으로 주입

═══════════════════ 대화 진행 ═══════════════════

③ 에이전트가 보강된 컨텍스트로 응답 생성

④ (선택) 에이전트가 중요한 정보를 직접 저장 결정
   → save_memory("사용자가 Q3 캠페인 담당자임을 밝힘")
   → 추측이나 PII는 저장 안 함

⑤ 토큰 한계 근접 시 자동 컨텍스트 압축
   → 오래된 대화 N개를 롤링 요약으로 교체
   → 최근 N개 원문 유지

═══════════════════ 세션 종료 후 (비동기) ═══════════════════

⑥ 에피소드 추출: LLM이 세션 전체를 구조화된 JSON으로 요약
⑦ 사실 추출: 기억할 만한 사실을 병렬로 추출
⑧ 모순 감지: 기존 기억과 비교 → CORRECTED 소스로 업데이트
⑨ 에피소드 저장: 중요도 기반 초기 relevance 점수 부여

═══════════════════ 야간 배치 ════════════════════

⑩ 시간 감쇄 적용 (반감기 기반 설계 예시):
   R(t) = R₀ × 0.5^(t / halflife)
   - 중요 결정/수정: halflife = 365일  ← 팀마다 다르게 조정
   - 일반 대화:     halflife = 90일
   - 단순 조회:     halflife = 30일

⑪ relevance < 0.5 → 검색에서 제외 (삭제 아님, 필터링)
⑫ 지식 그래프 커뮤니티 요약 갱신 (Zep 패턴)

여기서 핵심은 세션 종료 후 메모리 업데이트가 비동기라는 거예요. 응답 파이프라인을 막지 않아요. 프로덕션에서 동기 메모리 쓰기를 쓰면 응답 레이턴시에 그대로 더해지거든요.

그리고 검색할 때는 세 가지 신호를 함께 써요. 벡터 유사도만으로는 부족해요. 키워드 일치(BM25), 엔티티 매칭을 결합해서 정규화된 점수로 랭킹해요. 특히 고유명사나 날짜처럼 임베딩이 잘 안 되는 정보는 BM25가 훨씬 정확해요.

자주 하는 실수 6가지

실제 프로덕션에서 반복적으로 나타나는 문제들이에요.

1. 모든 걸 저장한다 — 가장 흔한 실수예요. 저장량이 늘수록 검색 노이즈가 커지고, 몇 주 지나면 정작 필요한 기억을 못 찾아요. “이 정보가 다음 대화에서도 유용한가?”를 기준으로 필터링 레이어를 반드시 두어야 해요. 추측, PII, 시스템 내부 지시어는 저장하지 않아요.

2. 메모리 쓰기를 응답 파이프라인에 넣는다 — 메모리 저장이 느리면 그게 그대로 응답 시간에 붙어요. 항상 세션 종료 후 비동기로 처리하고, 응답은 먼저 보내요.

3. 낡은 기억을 처리하지 않는다 — 높은 신뢰도로 저장된 “사용자의 직장”이 퇴사 후에도 계속 상위 검색 결과로 나와요. 시간 감쇄 + 모순 감지를 함께 써야 이걸 막을 수 있어요. 수정 사항은 CORRECTED 소스로 신뢰도 0.95를 부여해서 항상 우선 적용돼요.

4. user_id만으로 격리한다 — user_id 하나로는 부족해요. 같은 사용자라도 다른 에이전트, 다른 세션은 서로 격리되어야 할 수 있어요. (user_id, agent_id, session_id, org_id) 조합으로 네임스페이스를 구성해야 나중에 유연성이 생겨요.

5. 메모리를 단순 저장소로 본다 — 저장하고 검색하면 끝이라고 생각하기 쉬운데, 실제로 중요한 건 수명 주기 관리예요. 어떤 기억이 살아있고 어떤 기억이 죽었는지, 언제 승격하고 언제 폐기하는지. 저장 레이어는 쉬운 부분이에요.

6. 메모리 오염을 고려하지 않는다 — 에이전트가 외부 입력(이메일, 웹 콘텐츠, 사용자 메시지)을 기반으로 메모리를 저장하면, 악의적인 내용이 기억으로 주입될 수 있어요. 쓰기 시점에 입력 검증을 하고, 고위험 업데이트(역할 변경, 권한 관련)는 사람 승인을 거치는 게 좋아요.

어떤 메모리를 먼저 붙여야 할까

처음부터 모든 레이어를 구현할 필요는 없어요. 실제로 어떤 문제가 생기는지를 보면서 순서대로 추가하는 게 맞아요.

1단계 — In-context만 있는 상태: 대화 안에서는 잘 동작하지만 대화가 끊어지면 리셋돼요. 프로토타입에는 충분해요.

2단계 — Episodic 추가: 사용자가 “저번에 얘기했잖아요”라고 불평하기 시작할 때예요. mem0, Zep을 붙이면 며칠 안에 구현할 수 있어요.

3단계 — Semantic 추가: 도메인 지식이 필요할 때예요. 제품 문서, 정책, 기술 스펙 같은 것들이에요. 벡터 DB + RAG 파이프라인이 필요해요.

4단계 — Procedural 동적화: 사용자 역할이나 상황에 따라 다른 행동 패턴이 필요할 때, 시스템 프롬프트를 동적으로 구성해요.

각 단계에서 문제가 생기기 전에 미리 추가하면 복잡도만 올라가요. 타이밍은 사용자의 불편으로 결정하는 게 가장 정확해요.

에이전트의 기억은 결국 어떤 정보를 살아있게 유지할 것인가의 문제예요. 저장하는 것보다 관리하는 게 어렵고, 검색하는 것보다 낡은 기억을 처리하는 게 어렵거든요.

처음엔 In-context만으로 시작하고, 사용자가 느끼는 불편을 보면서 하나씩 레이어를 쌓아가세요. 메모리 아키텍처를 처음부터 완벽하게 설계하려다가 실제로 배포조차 못 하는 경우가 더 많아요.
