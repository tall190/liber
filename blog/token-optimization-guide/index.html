AI 토큰을 현명하게 쓰는 법: 낭비 패턴 인식부터 고급 기법까지

AILLM토큰최적화실무

어느 날 AI 사용 비용 청구서를 보고 멈칫한 적 있으세요? 저는 팀에 AI 도구를 붙이고 두 달쯤 지났을 때 그랬어요. 월말 리포트를 보니 예상보다 3배 가까이 나온 거예요. 근데 이상한 건, 팀이 “뭔가 대단한 걸 했다”는 느낌이 없다는 거였어요. 분명 열심히 썼는데 결과물이 그 비용을 정당화할 만큼인가, 솔직히 확신이 없었어요.

토큰 최적화 이야기를 꺼낼 때 흔히 “이렇게 프롬프트를 짧게 쓰면 됩니다” 수준으로 끝나는 경우가 많은데, 실제로는 그게 전부가 아니에요. 어느 타이밍에 어떤 접근을 써야 하는지, 단계가 있어요. 이 글에서는 입문자가 고수로 가는 여정을 따라가면서 각 단계에서 쓸 수 있는 기법들을 논문 근거와 함께 정리해볼게요.

토큰 최적화에도 단계가 있다

1단계: 최대한 써라 (최적화는 나중에)

AI를 처음 팀에 도입했을 때 토큰 최적화를 제일 먼저 걱정하면 안 돼요. 이 시기에 토큰을 아끼려다 사용성을 낮추면 팀이 AI 자체를 거부하게 돼요. 그게 훨씬 큰 손실이에요.

처음에는 그냥 많이 써야 해요. 뭐든 물어보고, 여러 번 수정하고, 긴 문서도 통째로 넣어보는 경험을 해야 나중에 “이건 AI가 필요한 작업이고, 이건 아니다”를 판단할 수 있게 돼요. 이 단계의 목표는 생산성 향상이지, 비용 절감이 아니에요.

2단계: 과도기 — 불필요한 곳까지 AI가 들어온다

사용성이 어느 정도 올라오면 이상한 일이 생겨요. AI가 만능처럼 느껴지기 시작하는 거예요. 간단한 정규식도 AI에게 물어보고, 2분이면 직접 쓸 수 있는 코드도 프롬프트를 3번씩 수정해가며 생성시켜요. 이 시기에 토큰 소비가 폭발적으로 늘어나는데, 문제는 그 상당 부분이 가치를 만들어내지 못하는 작업이에요.

전형적인 낭비 패턴들이 있어요.

  • 반복 작업을 매번 새로 설명한다: “PR 설명 써줘. 우리 팀 컨벤션은 이런데…”를 매번 복붙하는 경우
  • 컨텍스트를 통째로 넣는다: 관련 없는 코드도 “혹시 몰라서” 다 포함하는 습관
  • 검증 없이 여러 번 시도한다: 결과가 마음에 안 들면 그냥 “다시 해줘”를 반복
  • AI가 필요 없는 작업에 AI를 쓴다: grep으로 2초면 찾는 걸 AI에게 물어보는 식

3단계: 패턴 인식과 체계적 최적화

낭비를 알아채기 시작하면 그때부터 최적화가 의미 있어요. 이 단계에서 하는 일들이 이 글의 핵심이에요.

빠른 개선: 반복 패턴을 자동화하라

스킬과 MCP으로 반복 제거

가장 빠른 ROI가 나오는 영역이에요. 팀이 매번 같은 프롬프트를 쓰는 작업이 있다면, 그걸 스킬이나 MCP 툴로 만들어두는 게 맞아요.

예를 들어 “PR 설명 생성”을 매번 직접 하면 컨텍스트 설명 + 컨벤션 안내 + 실제 요청으로 1,500 토큰쯤 써요. 스킬로 만들어두면 “git diff 읽어서 PR 만들어줘” 한 문장이 전부예요. 같은 결과물을 200 토큰 안에 얻는 거예요.

이게 단순히 토큰 절약이 아니라 일관성도 올려줘요. 사람마다 다르게 프롬프트를 쓰면 결과물 품질이 들쭉날쭉한데, 스킬화하면 팀 전체가 같은 수준의 결과를 얻게 돼요.

프롬프트 구조화로 즉각적인 절감

잘 구조화된 프롬프트는 횡설수설한 프롬프트보다 30-50% 토큰을 덜 써요. 수치적 근거도 있어요. CloudZero의 2025년 분석에 따르면 프롬프트 최적화와 기본 캐싱만으로 며칠 안에 15-40% 비용 절감이 가능해요.

구체적으로는 이런 원칙들이에요.

❌ "우리 팀은 TypeScript를 쓰고 React도 쓰고 있고요, 
    Next.js 13 이상이고, 테스팅은 Jest랑 Testing Library를 쓰고 있어요. 
    CSS는 Tailwind를 쓰고 있고요. 그런데 아 물론 스타일드 컴포넌트도 
    일부 레거시에 남아있긴 해요. 암튼 이걸 고려해서..."

✅ "Stack: Next.js 13, TypeScript, Tailwind, Jest
    Task: [구체적 요청]"

중급 기법: 컨텍스트 최적화

컨텍스트가 길어질수록 비용이 선형으로 늘어나요. 근데 무조건 줄이면 안 돼요. IBM 연구자들은 단순히 컨텍스트를 늘리는 것보다 신중하게 선별된 예제들을 넣는 게 성능을 더 높인다는 걸 보여줬어요. 양보다 질이에요.

Lost in the Middle 문제

긴 컨텍스트가 무조건 좋지 않은 이유가 있어요. “Lost in the Middle” 현상인데요, 128K 토큰 규모에서 컨텍스트 중간에 있는 정보는 40% 정도 성능 저하가 발생해요. 10만 토큰짜리 문서를 다 넣었는데, 정작 모델이 중간 내용은 잘 못 참조하는 거예요.

중요한 정보는 컨텍스트의 앞이나 끝에 배치하고, 중간은 덜 중요한 것으로 채우는 게 효율적이에요.

LLMLingua: 프롬프트 압축 기술

더 적극적인 방법은 프롬프트 자체를 압축하는 거예요. Microsoft Research에서 만든 LLMLingua가 대표적인 도구예요. EMNLP 2023에서 발표된 이 연구는 작은 모델(GPT-2 수준)을 써서 프롬프트에서 중요하지 않은 토큰을 식별하고 제거해요.

결과가 꽤 인상적이에요. 최대 20배 압축에 성능 하락은 1.5 포인트 수준이에요. LongLLMLingua 버전에서는 GPT-3.5-Turbo 기준으로 토큰을 4분의 1로 줄이면서 오히려 성능이 17.1% 향상된 케이스도 있어요. 노이즈를 제거하니 모델이 더 잘 집중하게 된 거예요.

프롬프트 압축은 크게 두 가지 방식이에요.

방식원리특징
어휘 기반 (Lexical)중요하지 않은 토큰 제거블랙박스 모델에도 적용 가능
임베딩 기반 (Embedding)컨텍스트를 벡터로 압축더 높은 압축률, 파인튜닝 필요

실용적으로는 어휘 기반이 바로 쓸 수 있어서 더 많이 쓰여요.

RAG 정확도를 높여야 하는 이유

RAG(Retrieval-Augmented Generation)를 쓸 때 흔히 하는 실수가 “많이 가져오면 좋겠지”예요. 관련 문서 10개를 다 넣으면 뭔가 더 잘 답할 것 같은 느낌이 드는 거죠. 근데 실제로는 반대예요.

2025년 RAG 압축 연구에 따르면, 리랭커(Reranker)를 이용한 추출형 압축이 가장 효과적이에요. 정확도를 유지하면서 2-10배 압축을 달성해요. 오히려 노이즈 문서를 걸러내니 정확도가 올라가는 경우도 많아요.

핵심 원리는 이래요.

❌ 검색한 문서 10개 → 전부 LLM에 입력 (10,000 토큰)
   → 관련 없는 내용도 섞여서 혼란

✅ 검색한 문서 10개 → 리랭커로 상위 2개 선별 → LLM에 입력 (2,000 토큰)
   → 핵심만 집중 → 비용 80% 절감 + 정확도 향상

Reranker는 비용이 거의 없는 경량 모델이에요. Cross-encoder 계열 모델들은 수 밀리초 안에 관련성 점수를 줘요. 토큰을 아끼면서 정확도도 올릴 수 있는 가성비 최강 기법이에요.

계획으로 시행착오 자체를 줄여라

이 부분이 의외로 가장 큰 토큰 절감 효과를 줄 수 있는데, 잘 이야기 안 돼요.

개발 과정을 생각해볼게요. AI에게 “이 기능 만들어줘”라고 던졌다가 결과가 마음에 안 들어서 다시 요청하고, 또 수정하고… 이렇게 5번 반복하면 1번 잘 만든 것보다 5배 토큰을 쓰는 거예요. 근데 처음에 요구사항을 정확히 정의하고, 설계를 먼저 검토하고, 그 다음에 구현을 요청했다면 1-2번에 끝낼 수 있어요.

에이전트 워크플로우에서는 이게 더 심각해요. 50단계 에이전트가 각 단계마다 20K 토큰을 쓴다면 전체가 100만 토큰이에요. 계획 없이 시도-실패를 반복하면 이게 3-5배로 불어나요.

실용적인 접근은 이래요.

  1. 요구사항 명확화 먼저: “어떻게 만들어줘”보다 “이런 인터페이스로, 이런 제약 조건에서, 이런 결과를 내는 함수 만들어줘”
  2. 설계 검토 후 구현: 큰 작업은 먼저 접근법을 물어보고, 동의하면 구현 요청
  3. 검증 기준 사전 정의: “이런 케이스가 통과하면 완성”을 미리 말해두면 수정 루프가 줄어요

고급 기법: 논문 기반 접근

Chain of Draft: 추론 토큰 혁파

“생각하면서 풀어봐” (Chain of Thought, CoT) 방식은 복잡한 추론 문제에서 정확도를 크게 올려줘요. 근데 문제가 있어요. CoT는 토큰을 2-4배, 심하면 10-50배까지 더 써요.

Chain of Draft (CoD) 연구가 흥미로운 대안을 제시해요. 사람이 실제로 계산할 때처럼 중간 단계를 최대한 짧게 쓰는 방식이에요. 결과는 놀라웠어요. CoT와 거의 같은 정확도를 내면서 토큰은 7.6%만 써요. 같은 추론 능력을 90% 이상 적은 토큰으로 얻는 거예요.

CoT 예시:
"먼저 A를 계산해야 해요. A는 B와 C의 합인데요, B는... 
그러므로 A는... 이제 D를 구해야 하는데..."
→ 200 토큰

CoD 예시:  
"A=B+C=15, D=A×2=30, 답: 30"
→ 15 토큰

Token-Budget-Aware Reasoning

Thinking 모드를 쓰는 최신 모델(Claude, o1, DeepSeek-R1 계열)에서 특히 유용한 기법이에요. TALE (Token-Budget-Aware LLM Reasoning) 연구는 모델에게 “이 문제는 N 토큰 안에 풀어줘”라는 예산 제약을 주는 방식이에요.

결과: 평균 68.64% 토큰 감소, 정확도 하락은 5% 미만이에요. 모델이 제약 안에서 더 효율적으로 추론하도록 스스로 전략을 바꾸는 거예요.

Claude API에서는 thinking 파라미터의 budget_tokens로 직접 제어할 수 있어요.

response = client.messages.create(
    model="claude-opus-4-7",
    max_tokens=16000,
    thinking={
        "type": "enabled",
        "budget_tokens": 2000  # 추론 토큰 예산 제한
    },
    messages=[{"role": "user", "content": prompt}]
)

Batch API: 비동기 처리로 50% 절감

속도가 덜 중요한 작업이라면 Batch API가 가장 확실한 방법이에요. OpenAI, Anthropic, Google의 Batch API는 모두 약 50% 할인을 제공해요. 비동기 처리를 허용하는 대신 비용을 반으로 깎아주는 거예요.

대량 문서 분석, 배치 번역, 야간 리포트 생성 같은 작업에 딱 맞아요. 실시간이 필요 없는 작업을 Batch로 전환하는 것만으로 그 영역 비용의 절반이 줄어들어요.

Model Routing: 작업 난이도에 맞는 모델 선택

모든 작업에 최고 성능 모델을 쓸 필요가 없어요. 간단한 분류, 짧은 요약, 키워드 추출 같은 작업은 소형 모델로도 충분해요.

Opus/GPT-4 급 → 복잡한 추론, 코드 생성, 창의적 작업
Haiku/GPT-4o-mini 급 → 분류, 짧은 요약, 데이터 파싱

라우터를 만들어서 작업 복잡도를 판단하고 모델을 자동 선택하면, 전체 비용을 40-60% 줄인 사례들이 꽤 있어요.

언제 한 번에 많이 쓰는 게 나은가

직관과 반대인 케이스가 있어요. 토큰을 “아낀다”는 이유로 작업을 잘게 쪼개면 오히려 더 많이 쓰게 돼요.

잘게 쪼개면 손해인 경우:

  • 전체 파일을 조금씩 수정할 때: “1번 함수 고쳐줘” → 검토 → “2번 함수 고쳐줘” → 검토… 이렇게 하면 매번 컨텍스트를 다시 로드해요. 한 번에 “이 파일 전체를 리팩토링해줘”가 총 토큰이 더 적어요.
  • 의존 관계가 있는 작업: 연관된 여러 함수를 따로 수정하면 일관성 문제로 재작업이 생겨요. 처음부터 연관 부분을 다 보여주고 한 번에 처리하는 게 나아요.
  • 반복적인 컨텍스트 제공: 같은 배경 설명을 10번 넣느니, 한 번 긴 컨텍스트로 처리하는 게 효율적이에요.

반대로 쪼개야 하는 경우:

  • 독립적인 작업들: 서로 연관 없는 파일 5개를 각각 수정한다면 병렬로 처리하세요. 연결고리가 없으면 컨텍스트 공유 이점이 없어요.
  • 단순-복잡 혼재: 간단한 것과 복잡한 것을 묶으면 간단한 것도 큰 모델로 처리해요. 난이도별로 분리해서 라우팅하세요.

모델별로 전략이 다르다

2025-2026년 기준으로 모델 세대가 많이 바뀌었어요. 이걸 고려하지 않으면 예전에 통하던 최적화가 역효과를 낼 수 있어요.

컨텍스트 창 확대: Claude Sonnet 4는 1M 토큰, Gemini 2.5 Pro는 2M 토큰을 지원해요. 예전 모델 기준으로 “이건 컨텍스트에 못 넣겠다”고 판단했던 작업들이 이제 가능해졌어요. 근데 긴 컨텍스트도 Lost in the Middle 문제가 있으니, 단순히 다 넣는 게 아니라 구조적으로 배치해야 해요.

Thinking 모델: Claude Opus 4, o1, DeepSeek-R1 같은 모델은 내부 추론 토큰을 별도로 써요. 단순 작업에 이 모델들을 쓰면 추론 토큰이 과도하게 나와요. Thinking 모델은 복잡한 추론이 필요한 작업에만 써야 해요.

캐싱 전략: Anthropic의 Prompt Caching은 반복되는 시스템 프롬프트나 긴 문서를 캐시해요. 동일한 컨텍스트를 여러 번 쓰는 에이전트 워크플로우에서 특히 효과적이에요. 캐시 히트 시 입력 토큰 비용의 90%를 절감해요.

마무리: 최적화는 시기와 방법이 전부다

토큰 최적화를 정리하면 이렇게 돼요.

단계전략기대 효과
입문기최적화 말고 생산성 먼저팀 AI 활용도 확립
과도기낭비 패턴 기록, 반복 작업 식별비효율 구간 가시화
개선기스킬화, 프롬프트 구조화, 기본 캐싱15-50% 절감
최적화기RAG 정확도, 압축, 모델 라우팅50-80% 절감

근데 이 모든 최적화보다 효과적인 게 있어요. “이 작업에 AI가 정말 필요한가”를 먼저 묻는 거예요. grep으로 2초 만에 찾는 걸 AI에게 물어보지 않는 것, 이게 가장 확실한 토큰 절감이에요.

AI를 잘 쓴다는 건 많이 쓰는 게 아니라, 필요한 곳에 적절한 방법으로 쓰는 거예요. 낭비 패턴을 인식하고, 반복을 자동화하고, 복잡한 작업은 한 번에 잘 설계해서 던지는 것. 이 세 가지가 토큰 최적화의 핵심이에요.
