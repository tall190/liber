AI를 쌓는 순서 — 프롬프트에서 파인튜닝까지, 각 기술이 놓일 자리

AILLMFine-tuningRAG실무의사결정

AI 도입을 검토하다 보면 어느 순간 “파인튜닝을 해야 하나요?”라는 질문이 나와요. 보통 프롬프트를 며칠 써보고, 결과가 마음에 안 들면 바로 이 질문으로 넘어가는 경우가 많더라고요.

근데 파인튜닝은 여정의 끝에 있는 선택이에요. 끝까지 가봐야 파인튜닝이 진짜로 필요한지 아닌지가 보여요. 대부분의 문제는 그 전 단계에서 해결돼요.

그 여정이 어떻게 생겼는지, 각 기술이 어디에 놓이는지 — 그리고 파인튜닝과 셀프호스팅을 혼동하지 않는 방법까지 정리했어요.

실제 여정은 이렇게 생겼어요

실무에서 AI 기술을 쌓아가는 순서는 대개 이렇게 흘러요.

프롬프트 엔지니어링
    ↓ (반복 작업이 생기면)
스킬 / 매크로
    ↓ (외부 도구 연결이 필요하면)
MCP / Tool Use
    ↓ (자율 실행이 필요하면)
에이전트
    ↓ (지식 문제가 있으면 언제든)
RAG
    ↓ (행동 패턴 변경이 필요하면)
파인튜닝
    ↓ (비용/보안/오프라인이 중요하면)
셀프호스팅

“프롬프트 → RAG → 파인튜닝”으로 이해하는 분들이 많은데, 그건 ML 연구자 관점이에요. 실무에서는 스킬과 MCP, 에이전트가 그 사이에 들어와요. 그리고 RAG는 지식 문제가 생기는 시점이면 언제든 붙일 수 있는 레이어예요 — 파인튜닝 전후와 상관없이요.

각 단계가 어떤 문제를 풀고, 언제 다음 단계로 가야 하는지 살펴볼게요.

각 단계에서 실제로 무슨 일이 일어나는가

프롬프트 엔지니어링 — 시작점

API를 처음 연결하면 대부분 여기서 시작해요. 역할을 주고, 형식을 정하고, 예시를 넣고, 출력을 제어하는 법을 익혀요.

이 단계를 벗어나야 할 신호가 있어요. 같은 종류의 작업에 매번 긴 지시어를 반복하고 있을 때예요. “오늘도 어제와 같은 프롬프트 조합을 복사해서 쓰고 있다”가 느껴지면 다음 단계를 볼 때가 됐어요.

프롬프트 기법 자체가 궁금하다면 이 블로그의 프롬프트 엔지니어링 바이블을 보시면 돼요.

스킬 / 매크로 — 재사용 가능한 패턴

반복되는 프롬프트 조합을 하나의 스킬로 패키징해요. “계약서 요약”, “이메일 초안 작성”, “코드 리뷰” 같은 작업이 대표적이에요. Claude Code나 팀 내 도구에서 /리뷰처럼 호출하면 지정된 프롬프트 패턴이 실행되는 구조예요.

이 단계의 핵심은 지식을 외부에서 가져오지 않아도 되는 작업이에요. 모델 자체가 알고 있는 지식으로 충분한 작업들이죠.

MCP / Tool Use — 외부 세계와 연결

모델이 실시간 정보나 사내 시스템에 접근해야 할 때 MCP(Model Context Protocol)나 Tool Use를 붙여요. Slack 메시지를 읽거나, 데이터베이스를 쿼리하거나, 캘린더에 일정을 추가하는 것들이에요.

여기서부터 모델이 “읽기와 쓰기” 모두를 할 수 있게 되기 때문에 권한 범위 설계가 중요해져요. 처음엔 읽기 전용 Tool부터 시작하는 게 안전해요.

에이전트 — 자율 실행

사람이 매번 중간에 개입하지 않아도 여러 단계를 스스로 처리하는 구조예요. “이슈를 발견하면 → 원인 분석하고 → Slack에 보고하고 → Jira 티켓 생성”처럼요.

에이전트가 필요하다는 신호는 명확해요. 사람이 중간 확인자 역할을 반복적으로 하고 있을 때예요. 모델이 A를 보고 B를 판단해서 C를 실행하는 흐름이 자주 반복된다면 에이전트로 만들 수 있어요.

에이전트 설계와 구현에 대한 내용은 이 시리즈에서 별도로 다루고 있어요.

RAG — 지식 레이어

RAG(Retrieval-Augmented Generation)는 어느 단계에서도 붙일 수 있어요. 단, 풀려는 문제가 명확할 때 붙여야 해요.

RAG가 필요한 신호: 모델이 사내 문서를 모르거나, 최신 정보를 모르거나, 수백 페이지짜리 참조 문서가 있을 때예요.

RAG가 필요없는데 붙이는 경우: 응답 스타일이나 말투가 일관되지 않는 문제예요. 그건 지식 문제가 아니라 행동 문제거든요.

RAG와 파인튜닝 — 풀려는 문제가 다르다

이 둘을 같은 선택지로 보는 경우가 많은데, 원래부터 다른 문제를 풀고 있어요.

RAG파인튜닝
해결하는 문제지식 없음행동 패턴
적용 대상모델이 모르는 정보스타일, 형식, 말투
지식 업데이트문서만 교체하면 됨재학습 필요
설명 가능성출처 추적 가능왜 그렇게 반응하는지 불투명

“RAG를 붙이면 파인튜닝이 필요 없다”는 말은 반은 맞고 반은 틀려요. 지식 문제라면 RAG로 충분해요. 하지만 모델의 기본 행동 방식을 바꾸고 싶다면 RAG로는 안 돼요. 두 가지가 같은 스택에 함께 있는 것도 완전히 정상이에요.

파인튜닝의 실체 — 언제, 얼마나, 어떻게

파인튜닝은 모델에게 추가 학습을 시켜서 특정 행동 패턴이 기본값이 되게 하는 거예요. 프롬프트를 매번 길게 써야 했던 지시사항이, 아무 말 안 해도 그렇게 동작하게 되는 거죠.

파인튜닝이 진짜로 필요한 케이스

① 스타일이 강하게 고정되어야 하는 경우

법률 문서 작성, 의료 기록 요약, 금융 보고서처럼 특정 도메인의 언어와 형식이 엄격하게 정해져 있을 때예요. 프롬프트로도 어느 정도 제어가 되지만, 대규모 트래픽에서 일관성을 유지하려면 파인튜닝이 더 안정적이에요.

② 보안 때문에 컨텍스트에 데이터를 못 넣는 경우

의료 정보나 금융 거래 데이터처럼 API 요청에 담을 수 없는 민감한 정보가 있을 때예요. 모델이 그 패턴을 학습해서 내재화하는 방식으로 접근하는 거예요.

③ 매 요청마다 수천 토큰의 지시어를 반복하는 경우

시스템 프롬프트가 매우 길고, 이미 Prompt Caching을 적용했는데도 비용이 크다면 파인튜닝으로 지시어 자체를 줄이는 걸 검토할 수 있어요. 단, 이 경우는 Prompt Caching으로 먼저 해결되는 경우가 더 많아요.

파인튜닝이 필요없는데 하려는 오해

“응답이 들쭉날쭉해서” — Temperature를 낮추거나, 출력 형식을 구체적으로 명세하면 해결되는 경우가 대부분이에요.

“최신 정보를 모르는 것 같아서” — 지식 문제예요. RAG가 맞는 해법이에요. 파인튜닝으로 새 지식을 넣으려면 데이터를 다시 준비하고 재학습해야 해요. 지식이 자주 바뀐다면 파인튜닝은 유지보수 악몽이 돼요.

“사내 도메인 용어를 모르는 것 같아서” — 사내 용어집을 RAG로 제공하거나, 시스템 프롬프트에 용어 정의를 담는 게 먼저예요. 파인튜닝보다 훨씬 빠르게 해결돼요.

파인튜닝의 비용 구조

파인튜닝은 초기 비용과 운영 비용 모두 높아요.

데이터 준비
  형식·말투 조정: 입출력 쌍 50~100개
  도메인 지식 내재화: 500~1,000개 이상
  행동 방식 전반 변경: 수천 개 이상

학습 비용 (API 기반, OpenAI 기준)
  gpt-4o-mini 학습: $0.003 / 1K tokens
  학습 데이터 1,000개 × 평균 500 tokens = 약 $1.5

운영 비용
  파인튜닝된 모델은 base 모델보다 비쌈 (gpt-4o-mini 기준 약 1.5배)
  트래픽이 충분히 많아야 장기적으로 수지가 맞음

데이터 준비가 항상 학습보다 더 많은 시간이 걸려요. 레이블링, 검증, 정제까지 — 이 과정이 몇 달씩 걸리는 경우가 흔해요. 나쁜 데이터 1,000개보다 좋은 데이터 100개가 낫거든요.

셀프호스팅 ≠ 파인튜닝

이게 가장 자주 혼동되는 부분이에요.

셀프호스팅은 Llama, Mistral 같은 오픈소스 모델을 직접 서버에 올려서 쓰는 거예요. 모델 자체는 그대로예요. 훈련을 추가로 하는 게 아니라, 이미 학습된 모델을 인터넷 연결 없이 내 인프라에서 실행하는 거예요.

파인튜닝은 그 모델에 내 데이터로 추가 학습을 시키는 거예요. 셀프호스팅 모델 위에 파인튜닝을 할 수도 있지만, 셀프호스팅 자체가 파인튜닝은 아니에요.

셀프호스팅이 맞는 상황이 있어요.

  • 비용: 트래픽이 매우 많아서 API 비용이 감당이 안 될 때
  • 데이터 프라이버시: 요청 내용이 외부 서버에 나가면 안 될 때
  • 오프라인: 인터넷 연결이 없는 환경에서 써야 할 때
  • 단순 작업: Claude나 GPT가 과할 정도로 간단한 요약, 분류, 번역 작업

중요한 건 셀프호스팅 모델(Llama 8B, Llama 70B 등)은 상용 API보다 성능이 낮다는 거예요. 비용을 줄이는 대신 품질을 일정 부분 포기하는 거예요. 파인튜닝을 해서 그 격차를 줄일 수 있지만, 그 파인튜닝 자체가 또 다른 프로젝트가 돼요.

그래서 어디서 시작해야 하냐면

처음엔 항상 프롬프트예요. 빠르고, 저렴하고, 즉시 실험할 수 있어요.

결과를 반복해서 쓰게 되면 스킬로 만들고, 외부 도구가 필요하면 MCP를 붙이고, 자율 실행이 필요하면 에이전트를 만들어요. 그 과정에서 지식 문제가 생기면 RAG를 붙여요.

파인튜닝은 프롬프트와 RAG로 해결이 안 되는 행동 문제가 있을 때, 데이터가 충분히 준비됐을 때, 지식이 자주 바뀌지 않을 때 검토해요.

셀프호스팅은 API 비용이나 데이터 프라이버시 문제가 실제로 생겼을 때 고려해요.

세 가지 기술이 경쟁하는 게 아니에요. 각자 다른 레이어의 문제를 풀고, 여정의 다른 지점에 놓여요. 지금 있는 문제가 어느 레이어에 있는지를 먼저 보는 게 출발점이에요.
