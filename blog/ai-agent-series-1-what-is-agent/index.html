AI Agent란 무엇인가: LLM이 행동하기 시작할 때

AIAgentLLM기술

LLM을 처음 프로덕션에 붙여봤을 때 곧 벽에 부딪혀요. 사용자가 “지금 주문 상태 알려줘”라고 하면 LLM은 훌륭한 문장으로 “저는 실시간 데이터에 접근할 수 없어요”라고 답해요. 모델은 분명 영리한데, 실제로는 아무것도 할 수 없죠.

이게 LLM의 근본적인 한계예요. 텍스트를 이해하고 생성하는 건 잘 하지만, 세상과 상호작용하지는 못해요.

이 글에서는 LLM이 단순한 텍스트 생성기에서 벗어나 실제로 행동하는 Agent가 되는 원리를 다뤄요. [AI Agent 완전정복] 시리즈 1편으로, 기초 개념부터 실무 패턴까지 한 번에 정리해볼게요.

LLM과 Agent: 무엇이 다른가

LLM과 Agent를 나누는 기준은 하나예요: 행동 가능성(Actability).

LLM은 입력을 받아 출력을 생성해요. 반면 Agent는 같은 LLM을 두뇌로 사용하면서, 외부 세계와 상호작용하는 행동 루프를 추가한 시스템이에요.

기능LLM 단독Agent
외부 데이터 접근✗✓ (Tool 통해)
코드 실행✗✓
파일 읽기/쓰기✗✓
다단계 계획 실행✗✓
세션 간 기억 유지✗✓ (External Memory)

“오늘 팀 캘린더 빈 시간 찾아서 회의 잡아줘”는 LLM 단독으로는 불가능해요. Agent는 캘린더 API를 호출하고, 가능한 슬롯을 확인하고, 미팅을 직접 생성할 수 있어요.

Agent의 4가지 핵심 구성요소

1. Tool Use

Tool은 Agent가 외부 세계와 상호작용하는 인터페이스예요. 함수 하나가 Tool 하나예요.

LLM이 사용자 입력을 보고 어떤 Tool을 어떤 인자로 호출할지 결정하면, 실제 실행은 코드로 이뤄지고, 결과가 다시 LLM에 전달돼요.

프로덕션에서 자주 쓰이는 Tool 유형:

유형예시
검색웹 검색, DB 조회, 벡터 검색
코드 실행Python interpreter, 쉘 커맨드
파일 처리읽기, 쓰기, PDF 파싱
외부 API결제, 캘린더, Slack, 날씨
컴퓨터 제어브라우저 자동화, 마우스/키보드

2. Memory

Agent의 메모리는 4가지 층위로 나뉘어요.

유형내용구현
Working Memory현재 실행 중인 컨텍스트프롬프트 내 텍스트
Episodic Memory타임스탬프가 있는 과거 경험벡터 DB (외부)
Semantic Memory사실 기반 도메인 지식벡터 DB, 지식 그래프
Procedural Memory규칙과 스킬코드, 파인튜닝

실무에서 가장 자주 마주치는 건 Working Memory와 Episodic Memory예요. Working Memory는 컨텍스트 윈도우 크기에 제약이 있고, 긴 작업일수록 오버플로우 위험이 생겨요. Episodic Memory는 세션 간 기억을 유지하기 위해 외부 저장소에 저장해야 해요.

3. Planning

Planning은 복잡한 목표를 여러 단계로 나눠 실행하는 방식이에요. 가장 널리 쓰이는 패턴이 ReAct예요.

ReAct (Reasoning + Acting) 는 생각 → 행동 → 관찰을 반복해요.

Thought: 사용자가 "서울 내일 날씨 알려줘"라고 했다. 날씨 API를 호출해야 한다.

Action: get_weather(city="서울", date="tomorrow")

Observation: {"temp": 18, "condition": "맑음", "humidity": 45}

Thought: 정보를 받았다. 자연스럽게 전달한다.

Final Answer: 내일 서울은 맑고 18°C 예정이에요. 습도는 45%예요.

LLM이 답을 바로 생성하는 게 아니라, 매 스텝에서 “지금 뭘 해야 하는가”를 추론해요. 중간에 예상과 다른 정보가 나오면 계획을 수정하기도 해요.

4. Multi-agent 구조

태스크가 복잡해지면 단일 Agent로는 한계가 생겨요. Multi-agent는 여러 Agent가 역할을 나눠 협력하는 구조예요.

[Orchestrator]
      ↓
┌─────┼─────┐
[검색] [분석] [작성]

Orchestrator가 전체 계획을 세우고, 각 Sub-agent에게 구체적인 태스크를 위임해요. Sub-agent는 독립적인 컨텍스트 윈도우를 유지하기 때문에 병렬 처리가 가능하고, 최종 결과만 Orchestrator로 돌아와요.

이 구조가 중요한 이유는 단순해요. 하나의 Agent가 긴 작업을 처리하면 컨텍스트가 과부하되지만, Multi-agent로 나누면 각자 집중해서 처리할 수 있어요.

Agent Loop: 실제 동작 흐름

이 4가지 요소가 합쳐진 Agent는 다음 루프로 동작해요.

1. 사용자 입력
2. LLM이 다음 행동 결정
   ├── Tool 호출 필요 → 실행 → 결과를 컨텍스트에 추가 → 2로 이동
   └── 충분한 정보 확보 → 최종 답변 생성 → 종료

LLM이 “충분하다”고 판단하기 전까지 Tool 호출과 관찰을 반복해요. 이 루프가 Agent와 단순 LLM 호출의 차이예요.

프로덕션에서 검증된 사용 사례

2025년 기준 실무에서 검증된 Agent 활용 예시예요.

  • 코드 리뷰 자동화: PR을 읽고, 관련 코드 파일을 탐색하고, 개선점 제안
  • 데이터 분석: 자연어 질문 → SQL 변환 → 실행 → 결과 해석 → 시각화
  • 고객 지원: CRM 조회 → 주문 확인 → 환불 처리 → 이메일 발송 자동화
  • 리서치 자동화: 웹 검색 → 문서 요약 → 보고서 작성
  • DevOps: 알림 수신 → 로그 분석 → 원인 파악 → Slack 공유

이 작업들의 공통점은 여러 단계의 행동이 필요하다는 거예요. LLM 단독으로는 불가능하지만, Tool과 Planning이 갖춰진 Agent에서는 가능해요.

정리

LLM과 Agent의 차이는 결국 “생각하냐 vs 행동하냐”예요. Tool로 외부 세계와 연결하고, Memory로 상태를 유지하고, Planning으로 복잡한 목표를 달성해요.
