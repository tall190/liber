내 AI 옆에 전담 팀원을 두는 법 — Claude Agent 활용 가이드

AIClaudeAgent자동화실무개발

Skill로 반복 작업을 자동화하고, MCP로 외부 시스템을 연결하고, Plugin으로 그걸 팀에 배포했어요. 근데 막상 하루종일 Claude와 대화하다 보면 다른 문제가 생겨요.

코드 리뷰를 부탁했는데 파일을 20개씩 훑고, 그 중간 과정이 전부 대화창에 쌓여요. 다음 질문을 하려는데 이미 컨텍스트가 리뷰 로그로 가득해요. 결국 새 대화를 열게 되죠.

Agent(서브에이전트)는 이 문제를 해결하려고 만든 기능이에요. 특정 작업만 전담하는 AI 인스턴스를 따로 띄워서, 그 안에서 벌어지는 일은 메인 대화를 더럽히지 않고 결과만 가져오게 해요. 이 글은 Agent를 만드는 법부터 팀 공유, 자동화, 리서치 활용까지 정리해요.

Agent 만들고 쓰는 법

Before: 코드 리뷰가 필요할 때마다 “이 파일들 리뷰해줘, 스타일 가이드는 이거고, 이런 패턴은 지적해줘”를 매번 새로 설명해요. 리뷰 과정에서 나온 파일 탐색 로그, 중간 추론까지 전부 메인 대화에 쌓여요.

After: .claude/agents/code-reviewer.md 파일 하나로 전담 리뷰어를 만들어두면, “code-reviewer한테 리뷰 시켜줘”라는 한마디로 끝나요.

---
name: code-reviewer
description: 코드 변경사항을 스타일 가이드 기준으로 리뷰
tools: Read, Grep, Glob
model: sonnet
---

프로젝트 스타일 가이드(CLAUDE.md)를 기준으로 리뷰해요.
지적한 부분마다 파일:줄 번호를 붙여요.

필수 필드는 name, description 두 개뿐이에요. tools로 이 에이전트가 쓸 수 있는 도구를 제한할 수 있고(리뷰어에겐 Read/Grep만 주고 Edit은 빼는 식), model로 가벼운 작업엔 빠른 모델을, 복잡한 판단엔 상위 모델을 지정해요.

호출하는 방법은 세 가지예요. 자연어로 “code-reviewer 에이전트 써줘”라고 지정하거나, @agent-code-reviewer로 멘션하거나, .claude/settings.json에 기본 에이전트로 박아둘 수도 있어요.

에이전트를 쓸지 말지는 이 기준으로 판단하면 돼요 — 결과만 필요하고 과정은 안 궁금할 때 써요. 파일 20개를 뒤지는 탐색 과정, 여러 후보를 시도해보는 시행착오, 이런 건 서브에이전트 안에 가둬두고 저는 요약만 받아요.

그래서 메인 대화가 깨끗해져요. 리뷰를 5번 시켜도 컨텍스트엔 리뷰 결과 5개만 남고, 탐색 로그는 안 쌓여요.

팀이 함께 쓰는 법

Before: 저만 code-reviewer 에이전트를 갖고 있어요. ~/.claude/agents/에 저장했으니까요. 옆자리 동료는 매번 저한테 “그 프롬프트 뭐였죠?”라고 물어봐요.

After: 에이전트 파일을 프로젝트 저장소의 .claude/agents/에 넣고 git으로 커밋해요. 그러면 그 저장소를 pull받는 순간 팀 전체가 같은 에이전트를 갖게 돼요.

~/.claude/agents/          ← 나만 쓰는 개인 에이전트
프로젝트/.claude/agents/    ← 이 저장소를 쓰는 모두가 공유

우선순위는 프로젝트 설정이 개인 설정보다 위예요. 그래서 팀 표준 리뷰어를 프로젝트에 심어두면, 개인이 전역에 비슷한 이름의 에이전트를 갖고 있어도 프로젝트 것이 우선 적용돼요.

한 저장소를 넘어 여러 프로젝트에 배포하고 싶으면 Plugin으로 묶어요. 지난 글에서 다룬 것처럼, Plugin 안에 agents/ 디렉토리를 넣고 마켓플레이스에 올리면 @내플러그인:code-reviewer처럼 네임스페이스가 붙은 형태로 누구나 설치할 수 있어요.

그래서 “이 프롬프트 뭐였죠?” 같은 질문이 사라져요. 온보딩 문서 대신 저장소 자체가 팀의 AI 사용법을 담고 있는 거예요.

자동화하는 법

Before: 배포가 끝났는지 확인하려고 몇 분마다 직접 상태를 확인해요. 매일 아침 어제 커밋을 리뷰하는 것도 제가 기억해뒀다가 챙겨야 해요.

After: 자동화 방식이 네 가지 있는데, 상황마다 맞는 게 달라요.

방식트리거이럴 때
Hook도구 호출·세션 시작 같은 이벤트커밋 전 자동 검증처럼 즉각 반응이 필요할 때
WorkflowClaude가 짠 스크립트로 실행파일 50개를 같은 방식으로 고치는 대규모 작업
Routine클라우드 cron 스케줄매일 아침 코드 리뷰처럼 사람 없이 도는 무인 작업
/loop로컬 세션 내 반복배포 완료를 기다리는 것처럼 내가 지켜보는 동안의 반복

Hook은 “이벤트가 생기면 반응”하는 자동 센서예요. PreToolUse, PostToolUse 같은 시점에 걸어두면 특정 명령을 막거나 검증할 수 있어요.

Workflow는 여러 에이전트를 코드로 오케스트레이션해요. pipeline(), parallel() 같은 함수로 “이 에이전트 결과를 저 에이전트에 넘기기”를 짤 수 있어서, 사람이 하나씩 지시하기엔 너무 큰 작업에 써요.

Routine은 claude.ai 클라우드에서 cron으로 도는 방식이라 로컬 세션이 꺼져 있어도 실행돼요. /schedule로 등록하고, 유료 플랜이 필요해요. 아직 research preview(베타) 단계라 동작이나 제한은 바뀔 수 있어요.

/loop는 제일 가벼워요. 세션을 열어둔 채로 같은 프롬프트를 일정 간격으로 반복시켜요.

그래서 “제가 기억해뒀다가 챙기기”가 사라져요. 사람이 트리거하는 일과 시스템이 알아서 도는 일이 분리되는 거예요.

리서치·질의에 활용하는 법

Before: 복잡한 질문 하나를 조사하려고 검색 → 읽기 → 다음 검색어 생각 → 다시 검색을 반복해요. 관점 하나로만 파다 보니 놓치는 게 있어요.

After: 에이전트를 여러 개 동시에 띄워서 각자 다른 각도를 맡겨요. 이게 fan-out 패턴이에요.

질문: "이 마이그레이션 방식이 안전한가?"

에이전트 A → 락킹 동작 관점에서 조사
에이전트 B → 롤백 시나리오 관점에서 조사
에이전트 C → 유사 사례·공식 문서 관점에서 조사
        ↓
최종 에이전트가 세 결과를 취합해서 판단

Claude Code에는 이 패턴이 내장 기능으로도 있어요. /deep-research는 하나의 질문을 여러 검색으로 쪼개서 던지고, 나온 출처들을 서로 교차검증한 다음 근거가 약한 주장은 걸러내고 보고서를 만들어줘요.

Workflow의 parallel()로 직접 fan-out을 짤 수도 있어요. 파일 10개를 각각 다른 에이전트가 리뷰하게 하거나, 경쟁하는 가설 두 개를 동시에 검증시키는 식이에요.

그래서 검색 한 번, 관점 하나로 끝날 답변이 여러 각도로 교차검증된 답변이 돼요. 특히 “이 판단이 맞나 확신이 안 선다” 싶을 때, 관점을 나눠서 물어보는 게 같은 질문을 혼자 여러 번 곱씹는 것보다 빨라요.

Skill이 행동을, MCP가 연결을, Plugin이 배포를 담당했다면, Agent는 분업을 담당해요. 메인 대화는 저와 Claude가 대화하는 자리로 남겨두고, 시간이 걸리거나 반복적이거나 여러 관점이 필요한 일은 전담 에이전트에게 맡기는 거예요.

지금 자주 반복하면서 대화창을 더럽히는 작업이 있다면, 그게 첫 서브에이전트로 만들기 딱 좋은 후보예요.

Agent Team처럼 여러 에이전트가 실시간으로 서로 메시지를 주고받는 기능은 아직 실험적 단계라 이 글에서는 다루지 않았어요. Hook이 에이전트를 직접 트리거하는 정확한 문법도 공식 문서에 명시돼 있지 않아 확인이 더 필요해요.
