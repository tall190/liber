개인 지식베이스 RAG, Hit@5 70%에서 90%까지 — 260원으로 끝낸 최적화 기록

Vector DBRAGQdrantEmbeddingAI-Ready

지난 벡터 DB 4부작에서 임베딩이 뭔지, 청킹이 왜 중요한지, DB는 뭘 골라야 하는지 다뤘어요. 이론은 다 정리했는데, 정작 제 개인 지식베이스에 적용해보니 문제가 생기더라고요.

회사 업무 노하우, 기술 패턴을 모아둔 마크다운 파일이 500개가 넘어요. Qdrant에 벡터 인덱싱하고, MCP 서버로 Claude Code 세션에서 검색하는 구조예요. 근데 “이거 분명 적어뒀는데?” 싶은 걸 자꾸 못 찾더라고요. 검색 결과가 엉뚱한 문서를 가져오거나, 정작 원하는 파일이 상위 5개 안에 없는 경우가 많았어요.

이 글은 그 RAG 검색 정확도를 Hit@5 70%에서 90%까지 올린 과정이에요. 각 단계에서 뭘 했고, 얼마나 효과가 있었는지 수치로 보여드릴게요.

처음 구조 — 그럴듯한데 확인을 안 하고 있었어요

시작 구조는 이랬어요.

마크다운 문서 500+개
    ↓ 섹션 기반 청킹 (## 경계)
    ↓ BGE-M3 임베딩
    ↓ Qdrant 벡터 DB
    ↓ Hybrid 검색 (Dense + Keyword RRF)

나쁘지 않은 구조예요. BGE-M3은 한영 혼합에 강하고, Hybrid 검색은 의미 검색과 키워드 검색의 장점을 합쳐요. 여기까지는 교과서대로 잘 했어요.

근데 진짜 문제는 따로 있었어요. **“잘 되고 있는지 모른다”**는 거예요. 검색 결과를 보면 “대충 맞는 것 같은데?” 수준이지, 정확히 원하는 문서가 나왔는지 체계적으로 확인한 적이 없었거든요. 개선을 해도 좋아진 건지 나빠진 건지 판단할 방법이 없는 상태였어요.

이게 RAG 운영에서 제일 흔한 실수예요. 평가 없이 파이프라인부터 늘리는 것. 그래서 뭘 고치기 전에 먼저 측정 체계부터 만들기로 했어요.

Step 0. 평가 체계부터 만들기

모든 개선에 앞서 ground truth 데이터셋을 만들었어요. 30개의 질문-정답 쌍이에요.

- query: "기획 리뷰 판정 기준이 뭐야?"
  expected_files:
    - "knowledge/qa/planning-review-pattern.md"
  difficulty: easy
  category: qa

두 가지 지표로 측정했어요.

지표의미
Hit@5상위 5개 결과 안에 정답이 포함된 비율
MRR정답이 몇 번째에 나왔는지의 평균 역순위 (1위=1.0, 2위=0.5)

첫 측정 결과는 Hit@5 70%, MRR 0.428이었어요. 10개 중 3개는 원하는 문서를 못 찾고 있었다는 뜻이에요. 이제 개선할 기준선이 생겼어요 — 이걸 만드는 데 1시간이 안 걸렸는데, 이게 없었으면 아래 모든 개선이 그냥 “감”으로 한 게 됐을 거예요.

Step 1. Cross-Encoder Re-ranking — 가장 가성비 높은 개선

RAG에서 가성비 최고의 개선이 뭐냐고 물으면 저는 Re-ranker라고 답할 거예요.

Before: Bi-encoder(BGE-M3)로 query와 document를 각각 임베딩한 뒤 코사인 유사도로 비교해요. 빠르지만 query-document 쌍을 직접 비교하는 것보다 정밀도가 떨어져요.

After: Top-20까지 넉넉히 후보를 가져온 다음, Cross-Encoder로 재정렬해서 Top-5만 남겨요.

from sentence_transformers import CrossEncoder
reranker = CrossEncoder("BAAI/bge-reranker-v2-m3")

pairs = [(query, candidate.text) for candidate in top_20]
scores = reranker.predict(pairs)

sentence-transformers에 포함돼 있어서 별도 설치도 필요 없었어요.

Hit@5MRR
Before70.0%0.428
+Re-ranker80.0%0.536

+10%p, 구현 시간 30분, 추가 비용 0원이에요. medium 난이도만 놓고 보면 82%에서 100%로 뛰었어요. 이거 안 하고 계시면 지금 바로 넣으시면 돼요.

Step 2. HyDE + Source 가중치 — 질문과 문서의 임베딩 갭 줄이기

사용자 질문은 “~어떻게 해?” 같은 질문형이에요. 근데 문서는 “~방법은 다음과 같다” 같은 서술형이거든요. 이 둘의 임베딩 거리가 생각보다 멀어요.

HyDE는 질문을 가상 답변으로 바꿔서 임베딩하는 기법이에요. 원래는 LLM으로 가상 답변을 생성하지만, 저는 비용과 latency를 생각해서 규칙 기반으로 구현했어요.

def hyde_transform(query):
    # "어떻게 해?" → "방법과 절차는 다음과 같다."
    doc = re.sub(r"어떻게\s*(해|하면|돼)\s*[?]?$",
                 "방법과 절차는 다음과 같다.", query)
    return doc

LLM 호출 없이 latency 0으로 구현한 거라 정교하진 않은데, hard 난이도에서 효과가 있었어요.

여기에 Source 가중치도 더했어요. 제 지식베이스엔 직접 작성한 문서와 외부에서 가져온 문서가 섞여 있는데, 직접 작성한 쪽이 더 가치가 높잖아요.

SOURCE_BONUS = {
    "knowledge/":  0.10,
    "profiles/":   0.15,
    "agents/":     0.12,
    "external/":  -0.10,
}
Hit@5MRR
+Re-ranker80.0%0.536
+HyDE + Source83.3%0.581

hard 난이도가 25%에서 50%로 올라갔어요. 질문이 조금 간접적이어도 답을 찾기 시작한 거예요.

Step 3. Contextual Retrieval — 가장 근본적인 개선

여기가 진짜 핵심이에요.

기존 청킹의 문제를 하나 보여드릴게요. “실행 모드: sequential / parallel / group_parallel”이라는 청크가 있다고 해봐요. 이 텍스트만 보면 이게 무슨 플랫폼의 어떤 기능인지 알 수가 없어요. 임베딩도 마찬가지고요.

Contextual Retrieval은 각 청크에 문서 맥락을 붙여서 임베딩하는 기법이에요. Anthropic이 2024년에 발표한 방법인데, Contextual Embeddings와 Contextual BM25를 함께 쓰면 top-20 청크 기준 retrieval 실패율이 5.7%→2.9%로, 49% 줄어든다고 해요. Reranking까지 결합하면 67%까지 줄어든다고 하는데, 이 프로젝트도 이미 Step 1에서 Re-ranker를 적용해둔 상태라 비슷한 조합이에요. 저는 이 중 context prefix 부착 아이디어만 가져와 간소화해서 구현했어요. (Anthropic, Contextual Retrieval)

Before (규칙 기반, 비용 0)

def build_context_prefix(file_path, title, layer, tags):
    domain = path_to_domain(file_path)  # "knowledge/qa/" → "QA 방법론"
    return f"[문서: {title}] [도메인: {domain}] [레이어: {layer}] [태그: {tags}]"

embedding_text = f"{context_prefix}\n{chunk_text}"

이것만으로도 효과가 컸어요.

Hit@5MRR
+HyDE + Source83.3%0.581
+규칙 기반 Contextual86.7%0.609

특히 개인 프로필 검색이 0%에서 100%로 해결됐어요. “Jayden 커리어”를 검색하면 프로필 파일을 못 찾던 게, prefix에 “[도메인: 개인 프로필]“이 붙으면서 바로 찾게 된 거예요.

After (LLM 기반, 260원)

규칙 기반이 이미 좋았지만, LLM으로 더 풍부한 맥락을 생성할 수 있어요.

prompt = f"""다음은 '{title}' 문서의 한 청크입니다.
이 청크가 문서 전체에서 어떤 맥락에 해당하는지 1~2문장으로 요약하세요.
검색 시 이 청크를 찾을 수 있도록 핵심 키워드를 포함하세요."""

Gemini 2.0 Flash로 5,520개 청크를 10스레드 병렬 처리했는데, 약 100분 걸렸고 비용은 260원이었어요.

Hit@5MRR
+규칙 기반 Contextual86.7%0.609
+LLM Contextual90.0%0.638

hard 난이도가 25%에서 75%로, engineering 카테고리는 43%에서 86%로 올라갔어요. 규칙 기반이 큰 몫을 했고, LLM은 그 위에 추가로 몇 %p를 더 얹어준 거예요.

Step 4. 컬렉션 분리 — 경쟁하면 안 되는 문서 격리하기

마지막 문제가 하나 남아 있었어요. 직접 증류한 문서와 외부에서 가져온 원본 문서가 같은 벡터 DB 컬렉션에 섞여 있었거든요.

“기획 리뷰 판정 기준”을 검색하면 이런 일이 벌어졌어요.

1위: 외부 원본 페이지 (텍스트가 길어서 임베딩 매칭에 유리)
2위: 외부 원본 페이지 (비슷한 내용)
3위: 내 증류 문서 (← 이게 정답인데 3위)

외부 원본이 더 길고 상세해서 임베딩 유사도에서 이기는 거예요. source 가중치로 -0.10 패널티를 줬는데도 부족했어요.

해결책은 컬렉션 물리적 분리였어요.

synapse (내 지식)     ← 기본 검색 대상. 5,770 포인트
confluence (외부 원본) ← 필요할 때만 검색. 604 포인트

MCP 검색 도구에 source 파라미터를 추가해서 “내 지식만”, “외부만”, “둘 다” 중에 고를 수 있게 했어요.

Hit@5MRR
+LLM Contextual90.0%0.638
+컬렉션 분리90.0%0.651

Hit@5는 그대로인데 QA 카테고리 MRR이 0.594에서 0.738로 뛰었어요. 정답이 3위에서 1~2위로 올라왔다는 뜻이에요.

돌아보며 — RAG에서 진짜 중요한 건

측정 먼저예요. 평가 데이터셋 30개 만드는 데 1시간이 안 걸렸는데, 이게 없었으면 Re-ranker가 진짜 효과가 있는지, Contextual Retrieval이 정말 나은지 전혀 판단할 수 없었을 거예요.

Re-ranker는 지금 당장 넣으세요. 구현 30분, 비용 0원, 효과 +10%p. sentence-transformers의 CrossEncoder 한 줄이면 돼요.

Contextual Retrieval은 규칙 기반만으로도 충분히 효과적이에요. LLM 없이 파일 경로, 제목, 메타데이터만 조합해도 Hit@5가 83%에서 87%로 올라갔거든요. identity 검색이 0%에서 100%로 해결된 것도 규칙 기반의 공이에요. LLM은 그 위에 몇 %p를 더 올려준 정도예요. 이건 저만의 경험이 아니에요 — 외부 벤치마크에서도 HyDE 같은 쿼리 확장 기법은 효과가 들쭉날쭉한데 contextual retrieval은 꾸준히 개선폭을 보여준다는 결과가 나와요. 제 데이터에서 HyDE는 +3.3%p였고 Contextual Retrieval은 +6.7%p였던 것과 같은 패턴이에요.

양보다 질, 분리가 답이에요. 500개 문서를 하나의 컬렉션에 넣고 “많으면 좋겠지” 했던 게 틀렸어요. 성격이 다른 문서가 같은 공간에서 경쟁하면 정작 중요한 문서가 밀려나거든요. 직접 작성한 지식과 외부 원본을 분리한 게 MRR을 가장 크게 올린 개선이었어요.

결국 RAG는 IR 문제예요. RAG의 R은 Retrieval이잖아요. LLM이 아무리 똑똑해도 잘못된 문서를 가져오면 답변도 틀려요. 임베딩 모델 선택, 청킹 전략, re-ranking, contextual enrichment — 전부 검색 정확도를 올리기 위한 수단일 뿐이에요.

다음 단계

평가 데이터셋을 30개에서 100개로 늘릴 계획이에요. 실제 업무 중에 “못 찾겠다” 싶은 순간마다 1줄씩 추가하려고요. 주 1회 eval을 돌려서 RAG 건강도를 추적하고, 아직 남은 미스 3개는 유사 문서가 너무 많은 영역이라 chunk overlap이나 parent-child retrieval로 접근해볼 생각이에요.

검색이 90%를 넘으면 체감이 달라져요. “찾아보니 없더라”가 아니라 “찾아보니 있더라”가 기본이 되거든요. 그러면 지식을 쌓는 동기도 생기고, 자연스럽게 선순환이 시작돼요.

여러분 지식베이스는 지금 Hit@5가 몇 %인가요? 측정부터 한번 해보시는 걸 추천드려요.
