프롬프트 엔지니어링 바이블: 기본 설계부터 할루시네이션 방지까지

AIPrompt EngineeringLLM할루시네이션실무

프롬프트 엔지니어링만큼 논란이 많은 분야도 없어요. “그냥 잘 물어보면 되는 거 아냐?”라는 반응부터, “이건 아직 과학이 아니라 예술이다”는 말까지. 그 사이 어딘가에 진실이 있어요.

논란이 많은 이유는 두 가지예요. 하나는 모델이 너무 빠르게 바뀌어서 어제 통하던 기법이 오늘은 오히려 역효과를 낼 수 있다는 것, 다른 하나는 목적에 따라 정답이 달라진다는 거예요. 비용을 줄이려는 프롬프트와 정확도를 올리려는 프롬프트는 설계 방향이 반대예요.

이 글은 프롬프트 엔지니어링의 입문서가 아니에요. 실제로 AI 서비스를 설계하거나 운영하면서 부딪히는 질문들 — 어떻게 설계하고, 어떻게 개선하고, 어떻게 테스트하고, 할루시네이션을 어떻게 막는지 — 에 답하는 실전 레퍼런스예요. 길이에 상관없이 필요한 만큼 담았어요.

1. 프롬프트를 구성하는 요소들

프롬프트는 단일한 텍스트 덩어리가 아니에요. 잘 설계된 프롬프트에는 역할이 분리된 구성 요소들이 있어요.

[System Prompt]
너는 계약서 분석 전문가야. 반드시 근거 조항을 명시하고,
불확실한 내용은 "확인 필요"로 표시해.

[Context]
<document>
제3조: 계약은 서면 통보 후 30일 이내에 해지할 수 있다.
</document>

[User Message]
이 계약서에 해지 조항이 있나요? JSON으로 알려줘.

[Assistant Prefill]
{"result":

이 네 줄이 각각 다른 역할을 해요.

**시스템 프롬프트(System Prompt)**는 에이전트의 정체성과 행동 규칙을 정의해요. “너는 금융 전문가야”처럼 역할을 부여하거나, “반드시 출처를 명시해”, “모르면 모른다고 해”처럼 행동 제약을 걸어요. 모든 대화에 걸쳐 일관되게 적용되는 기반이에요.

**사용자 메시지(User Message)**는 실제 요청이에요. 맥락, 입력 데이터, 원하는 결과 형식이 여기에 들어가요.

**어시스턴트 프리필(Assistant Prefill)**은 Claude에서 특히 유효한 기법이에요. 응답의 첫 부분을 직접 작성해서 모델이 그 패턴을 이어가게 유도해요. {"result": 로 시작하게 하면 JSON이 나오고, `**분석 결과:**` 로 시작하게 하면 그 구조가 이어져요.

**컨텍스트(Context)**는 모델이 판단에 쓸 배경 정보예요. 참조 문서, 이전 대화, 데이터 등이 포함돼요.

이 네 가지가 명확히 구분되어 있을수록 프롬프트의 예측 가능성이 올라가요. 뒤섞이면 모델이 어느 역할로 응답해야 하는지 혼란이 생겨요.

2. 핵심 기법들: 무엇을 언제 쓰는가

Zero-shot

예시 없이 직접 요청하는 방식이에요. 현대 LLM은 이것만으로도 대부분의 일반 작업을 처리해요. 속도와 토큰 효율이 가장 좋아요. 단, 출력 형식이 중요하거나 엣지 케이스가 많은 작업엔 부족해요.

Few-shot

원하는 출력 형식의 예시를 2-5개 제공하는 방식이에요. 모델이 패턴을 따라가기 때문에 형식 일관성이 필요한 작업에 효과적이에요.

예시:

입력: "배송이 3일 늦었어요"
분류: 불만 / 카테고리: 배송

입력: "이 상품 환불 가능한가요?"
분류: 문의 / 카테고리: 환불

입력: "색상이 사진이랑 달라요"
분류: [모델이 여기서 패턴을 따름]

Few-shot에서 예시의 품질이 결과를 결정해요. 예외적인 케이스나 까다로운 케이스를 예시에 포함하면 그 패턴까지 학습시킬 수 있어요.

Chain of Thought (CoT)

“단계별로 생각해봐” 유도 방식이에요. 복잡한 수학 문제, 멀티스텝 추론, 법률/의료 판단처럼 중간 과정이 중요한 작업에서 정확도를 올려줘요.

하지만 2026년 기준으로 주의해야 할 사항이 있어요. Claude Opus 4, GPT-4o, o1, DeepSeek-R1 같은 추론 모델은 이미 내부적으로 사고 과정을 거쳐요. 이런 모델에게 “step by step으로 생각해봐”라고 하면 오히려 역효과가 날 수 있어요. SurePrompts의 2026년 가이드는 이를 명확히 정리해요.

“Let’s think step by step”은 이미 쓸모없거나 역효과예요. 추론 모델은 이미 답하기 전에 생각해요. 이 지시어는 모델이 이미 할당한 사고 예산을 낭비시켜요.

비추론 모델(Claude Haiku, GPT-4o-mini 등)에는 여전히 유효하고, 추론 모델에는 토큰 예산(budget_tokens)으로 사고량을 제어하는 게 더 효과적이에요.

XML 태그를 활용한 구조화

Claude에서 특히 효과적인 기법이에요. 입력의 각 부분을 XML 태그로 명확히 구분하면 모델이 어떤 정보가 어떤 역할인지 혼동하지 않아요.

<task>
  고객 문의를 분류하고 우선순위를 매겨줘.
</task>

<context>
  우리 서비스는 B2B SaaS이고, SLA에 따라 기업 고객은 4시간 내 응답이 필요해.
</context>

<input>
  {{customer_message}}
</input>

<output_format>
  JSON으로 반환. 필드: category, priority(1-5), suggested_response_template
</output_format>

태그 없이 같은 내용을 평문으로 쓰면, 모델이 어디까지가 맥락이고 어디서부터가 실제 입력인지 구분하기 어려워져요. 특히 입력 데이터에 지시어처럼 보이는 텍스트가 포함될 때 (프롬프트 인젝션) 이 구분이 중요해요.

출력 명세서(Output Contract) 작성

2026년 프롬프트 엔지니어링의 가장 중요한 변화는 “잘 써진 요청”에서 “명확한 성공 기준과 출력 명세서”로의 이동이에요.

❌ 예전 방식:
"이 코드를 리뷰해줘."

✅ 출력 명세서 방식:
"이 코드를 리뷰해줘.

성공 기준:
- 버그나 런타임 에러 가능성이 있는 부분을 모두 식별
- 각 이슈에 심각도 (critical / warning / info) 표시
- 수정 제안을 원본 코드와 함께 before/after 형식으로

제외:
- 스타일 관련 의견 (linter가 처리)
- 미래 기능 제안

출력 형식: 마크다운, 심각도 순으로 정렬"

요청이 명확할수록 모델이 추측하는 부분이 줄어들어요. 추측이 줄면 할루시네이션도 줄어요.

3. 모델별로 다르게 써야 하는 이유

같은 내용의 프롬프트라도 Claude, GPT, Gemini에서 결과가 다르게 나오는 건 각 모델의 훈련 방식과 아키텍처 차이 때문이에요.

Claude (Anthropic)

Claude는 XML 태그에 가장 잘 반응해요. Anthropic이 공식 문서에서 XML 구조화를 권장하고, 실제로 Claude는 태그로 역할을 분리하면 다른 모델보다 더 정확하게 각 부분을 처리해요.

Contract-style 명세서에도 강해요. 조건과 제약이 명시적으로 나열되면 그 계약을 꼼꼼히 따르는 경향이 있어요. 반면 모호한 요청에는 추론으로 빈칸을 채우는 대신 명확화 질문을 하거나 가정을 명시하는 편이에요.

Prefill 기법이 유효한 모델이에요. Assistant 턴의 첫 텍스트를 직접 제공하면 그 패턴을 이어가요.

response = client.messages.create(
    model="claude-sonnet-4-6",
    messages=[
        {"role": "user", "content": "이 계약서의 위험 조항을 JSON으로 추출해줘."},
        {"role": "assistant", "content": '{"risk_clauses": ['}  # Prefill
    ]
)

GPT (OpenAI)

GPT는 마크다운 문법에 잘 반응해요. ###, ---, 코드 블록 같은 구조가 Claude의 XML과 비슷한 역할을 해요.

GPT-5에서 특이한 점은 “think hard about this” 같은 표현이 실제로 내부 추론 모델로의 라우팅을 트리거한다는 거예요. OpenAI의 GPT-5 시스템 카드에 공식 문서화된 기능으로, 단순 지시어가 아니라 실제 라우팅 신호로 작동해요. GPT-4o에는 해당되지 않아요.

GPT의 Structured Outputs(Strict Mode)는 JSON 스키마를 Context-Free Grammar로 변환해서 스키마를 100% 보장해요. 정확한 출력 형식이 필요한 프로덕션 환경에서는 response_format을 활용하는 게 맞아요.

Gemini (Google)

Gemini는 짧고 직접적인 프롬프트에 더 잘 반응해요. Claude나 GPT보다 긴 프롬프트에서 중간 지시어를 놓치는 경향이 있어요. 메타 지시어(어떻게 답할지)를 태스크 설명보다 앞에 배치하는 게 중요해요.

멀티모달이나 문서 업로드를 활용하는 작업에서 특히 강해요. 표나 문서를 직접 첨부하면 텍스트로 설명하는 것보다 더 정확한 결과가 나와요.

4. 비용 최적화 vs 성능 최적화: 목적에 따라 방향이 반대다

프롬프트 설계는 목적에 따라 전략이 달라져요. 비용을 줄이는 방향과 정확도를 올리는 방향은 종종 충돌해요.

비용 최적화가 목적일 때

프롬프트 압축이 가장 직접적인 방법이에요. Microsoft Research의 LLMLingua는 소형 모델로 프롬프트에서 불필요한 토큰을 제거해요. 공식 벤치마크(GSM8K 기준)에서 최대 20배 압축 시 성능 하락이 1.5 포인트 수준으로 보고돼요. 단, 다른 데이터셋에서는 하락폭이 더 클 수 있어요.

수동으로 할 때는 이 원칙을 따라요.

  • 중복 표현 제거: “다음을 고려해서 잘 생각한 후에 신중하게” → “분석 기준:”
  • 인사말/배경 제거: 모델에게 하는 인사는 토큰 낭비예요
  • 결과물 길이 제한: 응답은 3문장 이내 명시
  • 불필요한 예시 축소: Few-shot을 3개에서 1개로 줄여도 충분한 경우가 많아요

모델 다운그레이드 라우팅도 중요해요. 모든 요청에 최고 성능 모델을 쓸 필요가 없어요. 분류, 단순 요약, 키워드 추출은 Claude Haiku나 GPT-4o-mini로 충분해요. 라우터를 두고 복잡도 기반으로 모델을 선택하면 전체 비용이 40-60% 줄어요.

Prompt Caching은 고정된 시스템 프롬프트가 있는 워크플로우에서 가장 효과가 커요. Anthropic의 Prompt Caching은 캐시 히트 시 입력 토큰 비용의 90%를 절감해요. 1,000 토큰 넘는 시스템 프롬프트가 있다면 캐싱을 먼저 붙여야 해요.

성능 최적화가 목적일 때

컨텍스트 강화가 핵심이에요. 모델이 판단에 필요한 정보를 모두 가지고 있어야 해요. 정보가 부족하면 모델은 추측으로 빈칸을 채우고, 그게 할루시네이션의 시작이에요.

명시적 제약을 추가할수록 정확도가 올라가요.

❌ "이 텍스트를 요약해줘"

✅ "이 텍스트를 요약해줘.
    - 원문에 있는 내용만 포함할 것
    - 원문에 없는 추론이나 해석은 포함하지 말 것
    - 불확실한 부분은 '원문에서 명확하지 않음'으로 표시
    - 3-5문장"

Self-Consistency도 효과적이에요. 같은 요청을 여러 번 생성하고 다수결이나 종합으로 최종 답을 만드는 방식이에요. 토큰이 N배 들지만 정확도가 크게 올라가요. 의료, 법률, 재무처럼 오답 비용이 높은 영역에서 쓸 만해요.

5. 할루시네이션: 종류부터 알아야 막을 수 있다

할루시네이션은 하나의 현상이 아니에요. Frontiers in AI의 2025년 리뷰와 바르셀로나 대학의 할루시네이션 분류 연구(2025) 등 LLM 할루시네이션 연구들이 공통으로 사용하는 분류 체계에 따르면 할루시네이션은 크게 두 범주로 나뉘어요.

내재적 할루시네이션 (Intrinsic Hallucination)

모델이 제공된 입력이나 컨텍스트와 직접 모순되는 내용을 생성하는 경우예요.

“이 계약서에 해지 조항이 있나요?” → 계약서에 명확히 해지 조항이 없는데 “제3조에 해지 조항이 있습니다”라고 답하는 것

입력된 정보를 잘못 해석하거나 무시하는 데서 발생해요.

외재적 할루시네이션 (Extrinsic Hallucination)

모델이 현실이나 학습 데이터로도 검증 불가능한 내용을 만들어내는 경우예요.

실제로 존재하지 않는 논문을 인용하거나, 없는 API 함수를 사용하거나, 실존하지 않는 통계를 제시하는 것

이 두 번째 유형이 AI 서비스에서 더 위험해요. 사용자가 그 내용을 신뢰하고 행동에 옮길 수 있거든요.

그리고 이를 좀 더 실용적으로 나누면 사실성(Factuality) 오류와 충실성(Faithfulness) 오류로 구분할 수 있어요.

  • 사실성 오류: 모델이 틀린 사실을 주장 — “세종대왕은 1423년에 태어났어요”
  • 충실성 오류: 입력이나 소스를 왜곡 — 문서 A에는 없는 내용을 요약에 포함

막는 방법이 달라요. 사실성 오류는 외부 데이터 접근(RAG)이나 불확실성 명시로 줄이고, 충실성 오류는 “입력 외 내용 포함 금지” 제약으로 줄여요.

6. 할루시네이션 방지 기법 8가지

기법 1: 불확실성 제약 (Uncertainty Constraints)

가장 단순하면서 효과적인 방법이에요. 모델이 모르면 모른다고 말하도록 명시적으로 허용하고 요구해요.

시스템 프롬프트에 반드시 포함:

"확실하지 않은 사실은 절대 단정하지 마세요.
모르는 내용에 대해서는 '확인이 필요합니다' 또는 
'이 부분은 제 학습 데이터에 포함되지 않을 수 있습니다'라고 명시하세요.
추측이나 추론을 사실처럼 제시하지 마세요."

모델이 “틀려도 뭔가 말해야 한다”는 압박을 받지 않게 안전한 탈출구를 주는 거예요. 이 한 줄이 없으면 모델은 모르는 것에 대해서도 그럴듯하게 만들어내는 쪽을 선택해요.

기법 2: 소스 제한 (Source Grounding)

모델의 응답 범위를 제공된 컨텍스트 안으로 제한해요.

"다음 문서의 내용만을 기반으로 답변하세요.
문서에 없는 내용은 '문서에서 찾을 수 없습니다'라고 답하세요.
외부 지식을 활용하거나 추론을 통해 빈칸을 채우지 마세요."

이 기법은 RAG 시스템에서 특히 중요해요. 검색된 문서 외의 내용을 모델이 임의로 추가하는 것을 막아요.

검증 가능한 출처 요청을 함께 써도 효과적이에요.

"모든 주장에 출처 문단 번호를 표시하세요.
출처를 명시할 수 없는 내용은 포함하지 마세요."

외부 검토자가 원본 문서와 대조해서 모든 주장을 확인할 수 있는 수준의 응답을 목표로 해요.

기법 3: 부정 지시어 (Negative Instructions)

“하지 말 것”을 명확히 써요. 긍정적 지시만큼 부정적 제약이 중요해요.

좋은 예:
- "사용자가 제공한 텍스트에 없는 수치나 날짜를 생성하지 마세요"
- "논문이나 연구를 인용할 때 직접 확인할 수 없는 것은 인용하지 마세요"
- "법률적 판단을 내리지 마세요. 가능성과 고려사항만 제시하세요"

단, 부정 지시어가 너무 많으면 모델이 필요한 내용도 생략해버릴 수 있어요. 명확히 문제가 되는 것만 골라서 제약해요.

기법 4: 단계적 검증 프롬프트 (Self-Verification Chain)

모델이 먼저 답변을 만들고, 그 답변을 스스로 검증하게 해요. 싱글 패스보다 오류를 줄이는 데 효과적이에요.

Step 1 프롬프트:
"아래 질문에 답해줘. [질문]"

Step 2 프롬프트 (Step 1 응답 포함):
"위 답변을 검토해줘.
- 사실로 주장한 것 중 확인이 필요한 항목은?
- 원본 데이터나 컨텍스트에 근거하지 않은 추론이 있는가?
- 수정이 필요한 부분이 있으면 수정된 버전을 제공해줘."

비용이 2배 들지만, 오류가 치명적인 의료, 법률, 재무 영역에서는 그 비용이 정당화돼요.

기법 5: 구조화된 출력으로 할루시네이션 범위 제한

자유로운 텍스트 생성은 할루시네이션이 스며들기 쉬워요. 출력 형식을 구조화할수록 모델이 임의로 내용을 추가할 여지가 줄어요.

# 나쁜 예: 자유 텍스트
"이 계약서를 분석해줘"

# 좋은 예: 스키마 강제
{
  "type": "object",
  "properties": {
    "parties": {"type": "array", "items": {"type": "string"}},
    "effective_date": {"type": "string"},
    "key_obligations": {"type": "array"},
    "risks_identified": {"type": "array"},
    "missing_clauses": {"type": "array"}
  },
  "required": ["parties", "effective_date"],
  "additionalProperties": false
}

2026년 구조화 출력 가이드에 따르면 신뢰도 수준이 세 단계로 나뉘어요.

  • 프롬프트만으로 JSON 요청: 80-95% 신뢰도 (프로덕션에 부족)
  • Function Calling / Tool Use: 95-99% 신뢰도
  • Native Structured Output (스키마 강제): 스키마 구조 100% 준수 보장

중요한 건 JSON Mode ≠ Structured Outputs이에요. JSON Mode는 유효한 JSON 문법을 보장할 뿐, 스키마를 보장하지 않아요. Native Structured Output의 100%는 스키마 형식 준수의 보장이에요. 내용의 사실 정확성을 보장하지는 않아요. 프로덕션에서는 반드시 스키마 강제 방식을 써야 해요.

기법 6: 온도(Temperature) 제어

Temperature는 모델의 창의성 수준을 조절해요. 높을수록 다양하고 창의적이지만 사실적 오류가 늘어요.

목적별 Temperature 가이드:

사실 기반 Q&A, 의료/법률/재무 정보:   0.0 - 0.2
코드 생성, 데이터 추출, 분류:          0.0 - 0.3
일반 요약, 번역, 분석:                 0.3 - 0.6
창의적 글쓰기, 브레인스토밍:           0.7 - 1.0

할루시네이션을 줄이려면 Temperature를 낮추는 게 가장 빠른 방법이에요. 단, 0으로 설정해도 할루시네이션이 완전히 사라지지는 않아요. LLM의 할루시네이션은 근본적으로 확률 분포 문제이기도 하지만, 훈련 데이터의 편향 문제이기도 하거든요.

기법 7: RAG로 외부 지식 접지 (Retrieval-Augmented Generation)

모델의 학습 데이터는 특정 시점에서 끊겨 있고, 도메인 특화 지식이 부족해요. RAG는 모델이 답변하기 전에 외부 데이터베이스에서 관련 정보를 가져와 컨텍스트에 포함시켜요.

RAG 시스템의 흐름:

사용자 질문
   ↓
임베딩으로 변환
   ↓
벡터 DB에서 관련 문서 검색
   ↓
검색된 문서 + 질문을 프롬프트에 포함
   ↓
모델이 "제공된 문서 기반"으로 답변

여기서 프롬프트 설계가 중요해요.

"다음 [N]개의 문서를 바탕으로 질문에 답하세요.
답변은 반드시 문서에 있는 내용만 포함해야 하며,
관련 내용이 없을 경우 '제공된 문서에서 관련 정보를 찾을 수 없습니다'라고 답하세요.
각 주장 뒤에 [문서 번호]를 표기해 출처를 명확히 하세요."

RAG에서 할루시네이션이 발생하는 패턴은 주로 두 가지예요. 검색된 문서가 질문과 관련이 없는데 억지로 연결하는 경우, 그리고 여러 문서의 내용을 섞으면서 원문에 없는 결합된 주장을 만드는 경우예요. “문서에 없으면 없다고 해”라는 명시적 제약이 이 두 가지를 모두 막아줘요.

기법 8: LLM-as-Judge (판단자로서의 LLM)

한 모델의 출력을 다른 모델(또는 같은 모델)이 검증하게 하는 방식이에요. 인간 검수의 대안으로 쓰거나, 자동화된 파이프라인에서 품질 게이트로 활용해요.

# Judge 프롬프트 예시
judge_prompt = """
다음 응답을 검토해줘.

[원본 질문]: {question}
[참조 문서]: {context}
[모델 응답]: {response}

아래 기준으로 평가해줘:
1. 사실성: 참조 문서와 일치하는가? (0-10)
2. 충실성: 질문에 직접 답하고 있는가? (0-10)
3. 할루시네이션: 참조 문서에 없는 내용을 주장하는가? (없음/경미/심각)
4. 수정 필요 사항: 있으면 구체적으로

출력 형식: JSON
"""

프로덕션에서는 모든 응답을 Judge로 통과시키기보다, 신뢰도 점수가 낮은 응답이나 고위험 카테고리(의료, 법률, 재무) 응답에만 적용하는 게 비용 효율적이에요.

7. 프롬프트를 코드처럼 관리하기

프롬프트는 코드예요. 그런데 많은 팀이 코드에는 Git을 쓰면서 프롬프트는 Notion이나 슬랙에 관리해요. 그 결과 어느 날 모델이 업데이트되면 왜 결과가 달라졌는지 원인을 못 찾아요.

버전 관리

prompts/
  ├── customer_support/
  │   ├── classify_v1.txt
  │   ├── classify_v2.txt       ← 현재 프로덕션
  │   └── classify_v3_test.txt  ← A/B 테스트 중
  ├── data_extraction/
  └── summarization/

프롬프트 파일에는 변경 이유를 주석으로 남겨요.

# v2.0 - 2026-03-15
# 변경: "불확실성 제약" 추가 (v1에서 존재하지 않는 조항을 인용하는 오류 발생)
# 변경: 출력 스키마를 JSON으로 강제 (v1의 자유 텍스트에서 파싱 오류 빈발)

평가 테스트 케이스

프롬프트를 바꿀 때마다 회귀 테스트가 돌아야 해요.

test_cases = [
    {
        "input": "계약서 해지 조항이 뭔가요?",
        "context": "본 계약은 60일 전 서면 통보로 해지 가능합니다.",
        "expected_contains": ["60일", "서면 통보"],
        "expected_not_contains": ["90일", "구두 통보"]
    },
    {
        "input": "위약금이 있나요?",
        "context": "본 계약서에 위약금 조항은 없습니다.",
        "expected_contains": ["위약금 조항은 없"],
        # 이 케이스에서 모델이 임의로 위약금을 만들어내면 안 됨
    }
]

새 프롬프트가 기존 테스트 케이스를 모두 통과한 뒤에 프로덕션에 배포해요.

8. 실전 체크리스트

프롬프트를 작성하거나 리뷰할 때 확인하는 항목들이에요.

기본 설계

  • 시스템 프롬프트와 사용자 메시지가 역할별로 분리되어 있는가?
  • 원하는 출력 형식이 명확히 정의되어 있는가? (스키마, 예시, 제약)
  • 모델이 모를 때 어떻게 응답해야 하는지 명시했는가?
  • 포함하지 말아야 할 내용이 부정 지시어로 명확히 정의되어 있는가?

할루시네이션 방지

  • “확실하지 않으면 모른다고 해” 제약이 시스템 프롬프트에 있는가?
  • 외부 지식보다 제공된 컨텍스트 우선 지시가 있는가?
  • 사실 기반 작업이라면 Temperature가 0.3 이하인가?
  • 프로덕션에서 JSON을 사용한다면 Native Structured Output을 쓰고 있는가?

비용 최적화

  • 중복 표현, 불필요한 배경 설명이 제거되어 있는가?
  • 고정 시스템 프롬프트가 1,000 토큰을 넘는다면 Prompt Caching을 쓰는가?
  • 작업 복잡도에 맞는 모델을 선택하고 있는가?
  • 단순 작업에 CoT나 Thinking 모드를 불필요하게 쓰고 있지 않은가?

운영

  • 프롬프트 파일에 버전이 있고 변경 이유가 기록되어 있는가?
  • 회귀 테스트 케이스가 있고 배포 전에 실행되는가?
  • 모델 업데이트 후 기존 프롬프트 동작을 확인하는 프로세스가 있는가?

마무리

프롬프트 엔지니어링이 “논란”인 이유는 고정된 답이 없기 때문이에요. 모델이 바뀌면 기법도 바뀌고, 목적이 다르면 접근도 달라요. 하지만 변하지 않는 것들이 있어요.

모델에게 추측을 강요하지 말 것, 모르면 모른다고 말할 수 있게 허용할 것, 출력 범위를 명확히 제한할 것, 프롬프트를 코드처럼 관리할 것.

이 네 가지가 지켜지는 시스템은 할루시네이션이 발생해도 원인을 찾고 고칠 수 있어요. 지켜지지 않는 시스템은 뭔가 이상하다는 걸 알아도 어디서 무엇이 잘못됐는지 알 수가 없어요. 그게 더 위험해요.
