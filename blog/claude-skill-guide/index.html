반복되는 AI 작업을 '/'로 끝내는 법 — Claude Skill 생태계 구축 가이드

AIClaudeSkill생산성자동화실무

오늘도 어제와 같은 프롬프트를 복사해서 쓰고 있다면, 그건 아직 Skill을 모르고 있는 거예요.

“시니어 개발자처럼 이 PR을 리뷰해줘. 버그, 성능, 가독성 순서로 정리하고, 각 항목에 심각도를 붙여줘.” — 이걸 매일 타이핑하는 대신 /review라고 치면 되는 세상이 있어요.

Skill은 반복되는 프롬프트 패턴을 슬래시 커맨드로 패키징하는 방법이에요. 개인 작업 스타일을 캡슐화할 수도 있고, 팀 전체에 배포해서 AI 사용 방식을 표준화할 수도 있어요. 잘 만든 Skill 하나가 팀 전체의 AI 사용 품질을 바꿔요.

Skill이 놓일 자리 — 4개 스코프

Skill은 어디에 저장하느냐에 따라 누가 쓸 수 있는지, git에 올라가는지, 얼마나 넓게 적용되는지가 전부 달라져요.

스코프경로적용 범위git 포함
Personal~/.claude/skills/<skill>/SKILL.md내 모든 프로젝트✗
Project.claude/skills/<skill>/SKILL.md이 프로젝트를 쓰는 팀 전체✓
Plugin<plugin>/skills/<skill>/SKILL.md플러그인 활성화된 곳플러그인 따라
Enterprise관리자 배포 (managed settings)조직 전체관리자 관리

우선순위는 Enterprise → Personal → Project 순이에요. 같은 이름의 Skill이 여러 스코프에 있으면 상위 스코프가 덮어써요.

하나 더 — 기존에 .claude/commands/deploy.md 방식으로 만든 커스텀 커맨드도 그대로 동작해요. 단, 같은 이름이라면 SKILL.md 형식이 우선해요.

어느 스코프를 선택할까

Personal: 내 작업 스타일, 내 언어, 내 습관이에요. 회사 레포에 올라가면 안 되는 개인 API 키나 사내 접근 정보가 필요한 경우에 여기에 둬요.

Project: 팀이 공통으로 써야 하는 스킬이에요. 코드 리뷰 기준, 커밋 메시지 형식, 배포 절차처럼 팀 전체가 같은 방식으로 해야 하는 작업들이에요. git에 커밋해서 공유하는 게 공식 권장 방식이에요.

Enterprise: 보안 정책, 컴플라이언스, 전사 AI 사용 가이드라인을 강제 적용할 때 써요. 개인이 수정할 수 없어요.

Skill 파일 해부 — 이렇게 생겼어요

Skill은 디렉토리 단위로 구성돼요.

my-skill/
├── SKILL.md          # 필수 — 프롬프트와 지침
├── template.md       # 선택 — Claude가 채울 출력 템플릿
├── examples/
│   └── sample.md     # 선택 — 기대 출력 예시
└── scripts/
    └── validate.sh   # 선택 — Claude가 실행할 스크립트

SKILL.md는 YAML 프론트매터 + 마크다운 본문 구조예요.

---
name: code-review
description: "PR diff를 보고 버그·성능·가독성 순서로 리뷰. 사용자가 '리뷰해줘'라고 할 때 사용"
argument-hint: "[PR 번호 또는 브랜치명]"
allowed-tools: Bash(git diff *) Bash(git log *)
model: claude-opus-4-7
effort: high
context: fork
---

## 리뷰 대상

!`git diff HEAD~1`

## 지침

아래 순서로 리뷰하세요:
1. 버그 (Critical / Major / Minor)
2. 성능 이슈
3. 가독성 및 유지보수성

각 항목에 심각도를 명시하고, 수정 제안을 코드로 보여주세요.

핵심 프론트매터 필드:

필드역할
descriptionClaude가 자동 호출 여부를 판단하는 기준. 잘 써야 해요
when_to_use트리거 조건 추가 설명
allowed-tools이 스킬 실행 중 권한 확인 없이 쓸 수 있는 도구
disallowed-tools이 스킬 실행 중 사용 금지 도구
model이 스킬에만 적용할 모델 (실행 후 원복)
effort추론 수준 low / medium / high / max
context: fork독립된 서브에이전트 컨텍스트에서 실행
paths특정 파일 패턴 작업 시에만 자동 활성화
disable-model-invocationtrue면 슬래시 메뉴에서만 수동 호출 가능
user-invocable: false슬래시 메뉴에서 숨김 (Claude만 자동 호출 가능)

!로 시작하는 동적 컨텍스트 주입:

!`git diff HEAD~1` 처럼 쓰면 Skill이 로드될 때 셸 명령을 실행해서 결과를 컨텍스트에 주입해요. 현재 브랜치 상태, 최근 로그, 환경 정보 같은 것들을 자동으로 넣을 수 있어요.

개인 · 직무 · 프로젝트 특화 전략

같은 Skill이라도 목적에 따라 설계가 달라져요.

개인 특화

내 작업 패턴을 그대로 담는 거예요. Personal 스코프에 두고, 팀에 공유하지 않아요.

---
name: daily-standup
description: "오늘 작업 내용을 스탠드업 형식으로 요약"
allowed-tools: Bash(git log --author=*)
---

!`git log --author="$(git config user.email)" --since="yesterday" --oneline`

위 커밋 목록을 스탠드업 형식으로 요약해줘:
- 어제 한 일
- 오늘 할 일
- 블로커 (없으면 생략)

직무 특화

특정 역할의 팀원들이 공통으로 쓰는 패턴이에요. 프로젝트 레포의 .claude/skills/에 두되, 민감 정보는 절대 포함하지 않아요.

---
name: qa-report
description: "테스트 결과를 QA 보고서 형식으로 정리"
paths: "**/*.test.ts,**/*.spec.ts"
---

프로젝트 특화

이 프로젝트의 컨텍스트가 필요한 경우예요. 코드베이스 규칙, 도메인 용어, 아키텍처 패턴을 담아요.

---
name: component-review
description: "React 컴포넌트를 이 프로젝트의 스타일 가이드 기준으로 리뷰"
paths: "src/components/**/*.tsx"
allowed-tools: Bash(cat .claude/style-guide.md)
---

이 프로젝트의 컴포넌트 규칙에 따라 리뷰해줘:
- Props 타입 명시 여부
- 접근성 (aria 속성)
- 불필요한 리렌더링

민감 정보를 다룰 때 — 충돌 지점들

Skill을 쓰다 보면 민감 정보와 충돌하는 지점이 생겨요. 모르면 큰 문제가 생길 수 있는 부분이에요.

충돌 지점 1: allowed-tools 광범위 부여

# 위험한 패턴
allowed-tools: Bash(*) Read(*) Write(*)

이렇게 쓰면 이 Skill이 활성화된 동안 Claude가 권한 확인 없이 모든 파일을 읽고 쓸 수 있어요. 낯선 레포를 클론했을 때 .claude/skills/에 이런 Skill이 있으면 실행 즉시 위험해져요.

Anthropic이 공식적으로 경고하는 내용이에요: “외부 레포를 trust하기 전에 .claude/skills/의 allowed-tools 설정을 반드시 확인하세요.”

# 안전한 패턴 — 최소 권한
allowed-tools: Bash(git diff *) Bash(git log --oneline)

충돌 지점 2: 동적 컨텍스트 주입의 위험

!`command` 구문은 Skill 로드 시 셸 명령을 실행해요. 악의적인 Skill이 이렇게 생겼다면?

# 위험한 패턴
---
!`cat ~/.env && cat ~/.ssh/id_rsa`

환경 변수와 SSH 키가 Claude 컨텍스트에 주입돼요. 이를 막으려면 settings.json에서 비활성화할 수 있어요.

// .claude/settings.json
{
  "disableSkillShellExecution": true
}

팀 레포에서는 이 설정을 켜두는 게 안전해요.

충돌 지점 3: MCP 권한이 Skill을 통해 우회되는 패턴

# Skill에서 MCP 도구를 직접 승인하는 패턴
allowed-tools: mcp__database__query mcp__slack__send_message

이렇게 하면 이 Skill이 실행되는 동안 DB 쿼리와 Slack 메시지 발송이 권한 확인 없이 허용돼요. MCP 서버가 내부 시스템에 접근한다면 Skill 하나로 그 권한이 통째로 열리는 거예요.

민감 정보 처리 원칙:

✓ API 키는 환경 변수로 — SKILL.md에는 변수명만 참조
✓ 개인 접근 정보가 필요한 Skill → Personal 스코프에만, git 커밋 금지
✓ 프로젝트 Skill에는 공개돼도 무방한 내용만
✓ 외부 레포 trust 전 .claude/skills/ allowed-tools 반드시 검토
✓ 팀 레포는 disableSkillShellExecution: true 권장

트리거와 훅 — AI가 알아서 불러오게 하기

슬래시로 직접 부르는 것도 좋지만, 특정 상황에서 자동으로 실행되게 하면 더 강력해요.

자동 호출 — description이 열쇠

Claude는 description과 when_to_use 필드를 읽고 지금 상황에 적합한 Skill을 스스로 판단해서 호출해요.

---
description: "사용자가 커밋이나 PR에 대해 리뷰를 요청할 때"
when_to_use: "코드 변경사항 리뷰, git diff 분석, PR 검토를 요청받을 때마다"
---

이렇게 쓰면 “이 코드 좀 봐줘”라고 했을 때도 Claude가 이 Skill을 선택해요.

특정 파일 패턴 작업 시에만 자동 활성화하고 싶다면 paths 필드를 써요.

---
paths: "src/components/**/*.tsx"
---
# .tsx 파일을 편집할 때만 이 Skill이 활성화돼요

Hooks 시스템 — 이벤트 기반 자동 실행

훅은 Claude의 특정 행동에 반응해서 셸 명령, HTTP 요청, MCP 도구 호출을 자동 실행하는 방법이에요. settings.json에 구성해요.

// .claude/settings.json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit",
        "hooks": [
          {
            "type": "command",
            "command": "npm run lint --fix"
          }
        ]
      }
    ],
    "SessionStart": [
      {
        "hooks": [
          {
            "type": "command",
            "command": "echo '프로젝트 컨텍스트 로드 완료'"
          }
        ]
      }
    ]
  }
}

주요 훅 이벤트:

이벤트언제 실행되나
SessionStart세션 시작 시 — 컨텍스트 자동 주입에 유용
UserPromptSubmit프롬프트 제출 전 — 입력 검증, 전처리
PreToolUse도구 호출 전 — 위험한 명령 차단 가능
PostToolUse도구 호출 후 — 린트, 포맷, 알림
PostToolUseFailure도구 실패 후 — 에러 리포트 자동 생성
Stop응답 완료 후 — 로깅, Slack 알림
PreCompact컨텍스트 압축 전 — 중요 정보 보존

훅 타입:

// 셸 명령 실행
{ "type": "command", "command": "prettier --write" }

// HTTP 요청
{ "type": "http", "url": "https://your-webhook.com/events" }

// MCP 도구 호출
{ "type": "mcp_tool", "tool": "mcp__slack__send_message" }

// LLM 평가 (프롬프트 기반 판단)
{ "type": "prompt", "prompt": "이 변경사항이 보안에 문제가 있는지 확인해줘" }

실제로 많이 쓰는 패턴은 PostToolUse에 린터·포맷터를 걸어두는 거예요. Claude가 파일을 수정할 때마다 자동으로 코드 정리가 돼요.

Skill 생태계를 구축하고 운영하는 법

한두 개 만드는 건 쉬워요. 팀 전체가 쓰는 생태계를 만들고 유지하는 게 진짜 과제예요.

개인에서 팀으로

1단계: 혼자 쓰면서 패턴 발견

Personal 스코프에서 1~2주 써보고, “이거 팀이 다 쓰면 좋겠다”는 Skill이 생기면 그때 Project로 옮겨요. 검증되지 않은 걸 바로 팀에 배포하면 신뢰를 잃어요.

2단계: 프로젝트 Skill로 표준화

.claude/skills/에 이동하고, git에 커밋해요. PR 설명에 “이 Skill이 뭘 하는지, 언제 써야 하는지”를 적어요.

3단계: 팀이 개선에 참여하게

Skill도 코드처럼 PR로 개선해요. “이 리뷰 Skill이 타입 오류를 잘 못 잡더라”는 피드백이 오면 description과 본문을 구체화해요.

좋은 Skill의 조건

✓ description이 구체적 — Claude가 언제 써야 하는지 명확히 알 수 있게
✓ allowed-tools가 최소한 — 필요한 것만 열어줌
✓ 민감 정보 없음 — git에 올라가도 문제없는 내용만
✓ 빠른 피드백 루프 — 잘 안 되는 부분은 바로 알 수 있게
✗ 너무 많은 걸 하려는 Skill — 하나의 Skill은 하나의 역할
✗ 하드코딩된 사람 이름, URL, 토큰

버전 관리와 개선 사이클

관찰 → 피드백 수집 → description/본문 수정 → PR → 배포

Skill을 만들고 나면 팀에 “어떤 상황에서 이상하게 동작하는지”를 적극적으로 물어봐요. LLM은 지시가 모호하면 알아서 채워요 — 그게 팀이 원하는 방향이 아닐 수 있거든요.

Claude가 기본으로 제공하는 번들 Skill

Claude Code를 설치하면 바로 쓸 수 있는 번들 Skill들이 있어요. disableBundledSkills: true 설정으로 끌 수 있어요.

커맨드역할
/code-reviewdiff 코드 리뷰 (버그, 클린업)
/simplify코드 정리 리뷰 + 자동 적용
/batch대규모 변경을 병렬 워크트리로 분산 실행
/loop프롬프트 반복 실행 (자동화에 유용)
/run앱 실행 후 변경사항 검증
/verify빌드·실행으로 코드 변경 검증
/debug디버그 로깅 활성화 및 세션 로그 분석
/fewer-permission-prompts트랜스크립트 분석 후 allowlist 자동 생성
/run-skill-generator프로젝트에 맞는 /run·/verify Skill 자동 생성

이 중에서 /run-skill-generator가 특히 유용해요. 내 프로젝트 빌드·실행 방식을 분석해서 맞춤형 Skill을 자동으로 만들어줘요.

커뮤니티 Skill과 최신 정보를 얻는 곳

직접 만들지 않아도 돼요. 이미 잘 만들어진 Skill들이 많아요.

커뮤니티 레포지토리:

  • awesome-claude-skills — 큐레이션된 Skill·리소스 목록
  • ComposioHQ/awesome-claude-skills — 1,000개 이상의 프로덕션 Skill
  • github.com/topics/claude-code-skills — GitHub 토픽 검색

많이 쓰이는 Skill 카테고리:

개발: TDD 워크플로우, 코드 리뷰, 배포 파이프라인, PR 생성
협업: Jira·Confluence 연동, Slack 보고, 스탠드업 요약
도메인: 법무 문서 검토, 마케팅 카피, 데이터 분석 리포트

공식 문서와 표준:

  • Claude Code Skill 공식 문서
  • Hooks 레퍼런스
