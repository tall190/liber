처음에는 그냥 물어보면 됐다.

"이 코드 뭐가 문제야?" 하면 답해줬다. "리팩터링해줘" 하면 해줬다. 충분했다. 아니, 그때는 그게 충분한 줄 알았다.

그런데 하다 보니 알게 됐다. 이건 내가 루프를 닫고 있는 거라는 걸. AI가 답하면 내가 판단하고, 내가 다음 질문을 던지고, AI가 또 답하고. 루프의 중심에 항상 내가 있었다. AI는 그냥 도구였다.

그리고 누군가 생각했다. 루프를 AI에게 넘기면 어떻게 될까?

그게 에이전트의 시작이었다. 그리고 그때부터 새로운 문제들이 하나씩 터졌다. 이 글은 그 문제들과, 그 문제들을 해결하기 위해 등장한 도구들의 이야기다.

---

## 1단계: LLM — 내가 루프를 닫는다

LLM은 질문에 답하는 기계다. 정확하게는, 다음 토큰을 예측하는 기계인데, 그 예측이 너무 잘 되다 보니 대화처럼 보인다.

```
[LLM 시대]

나 → 질문 → LLM → 답 → 나 → 판단 → 나 → 다음 질문 → ...
```

내가 루프를 닫는다. 이게 핵심이다. AI는 내가 물어볼 때만 일한다. 내가 없으면 아무것도 안 한다.

이 구조의 장점은 명확하다. 내가 모든 걸 본다. 내가 모든 걸 통제한다. AI가 이상한 방향으로 가면 내가 잡는다.

단점도 명확하다. 나는 항상 거기 있어야 한다.

---

## 2단계: Agent — 루프를 위임한다

어느 시점에, 이런 생각이 생겼다. "내가 목표만 주면, AI가 알아서 계획하고 실행하면 안 되나?"

그게 에이전트다.

```
[Agent 시대]

나 → 목표 → Agent → 계획 → 실행 → 관찰 → 다음 행동 → ...
                      ↑__________________________________|
                      (루프를 Agent가 닫는다)
```

루프가 AI 안으로 들어갔다. 나는 목표를 주고 결과를 받는다. 중간 과정은 AI가 처리한다.

LLM과 Agent의 차이는 여기에 있다.

| | LLM | Agent |
|---|---|---|
| 루프 주체 | 사람 | AI |
| 입력 | 질문 | 목표 |
| 출력 | 답 | 결과 |
| 도구 | 없음 | 있음 (파일 읽기, 코드 실행...) |
| 내 역할 | 판단자 | 목표 설정자 |

Claude Code가 하는 일이 바로 이거다. "이 버그 고쳐줘"라고 하면, 파일을 읽고, 문제를 분석하고, 코드를 수정하고, 테스트를 돌리고, 결과를 알려준다. 내가 중간에 개입하지 않아도.

그런데 에이전트를 쓰기 시작하자마자 첫 번째 문제가 터졌다.

---

## 3단계: Subagent — 컨텍스트가 넘친다

에이전트가 일을 하면 대화가 길어진다. 파일 내용, 검색 결과, 에러 로그, 실행 결과... 이게 다 컨텍스트 창에 쌓인다.

컨텍스트 창은 유한하다. Claude Sonnet도, Opus도, 결국 한계가 있다. 그리고 컨텍스트가 길어질수록 성능이 떨어진다. 초반에 했던 맥락을 잊어버린다. 비용도 늘어난다.

더 큰 문제가 있다. 조사하는 일과 실행하는 일이 섞인다. "이 모듈 전체를 분석해줘" 하면, 수백 개 파일을 읽은 결과가 메인 대화에 다 쌓인다. 나는 그 상세한 내용이 필요 없는데. 요약만 보면 되는데.

그래서 나온 것이 Subagent다.

```
[Subagent 구조]

메인 대화
├── Claude (메인)
│   └── "이 모듈 분석해줘"
│       ↓
│   [Subagent 생성]
│       └── Subagent (자기 컨텍스트 창)
│               ├── 파일 100개 읽음
│               ├── 분석 수행
│               └── → "핵심 문제 3가지 발견" (요약만 반환)
│       ↓
│   메인 대화에는 요약만 남음
```

Subagent는 자기 컨텍스트 창을 가진다. 거기서 실컷 탐색하고, 요약만 돌려보낸다. 메인 대화는 깨끗하게 유지된다.

여기서 용어를 짚고 넘어갈 필요가 있다. "Agent"와 "Subagent"는 타입이 아니라 **관계**를 나타내는 말이다. 부모 세션이 생성하면 Subagent, 사람이 직접 실행하면 Agent다. `.claude/agents/`에 정의한 같은 파일이 Claude가 대화 중 자동으로 위임하면 Subagent로, `claude --agent code-reviewer`처럼 사람이 직접 실행하면 Agent로 동작한다. 무엇인지가 아니라 누가 만들었느냐가 기준이다.

Claude Code에는 기본 Subagent가 있다.

**Explore** — 코드베이스 탐색 전용. 읽기만 하고 쓰지 않는다. 빠른 Haiku 모델로 돌아간다. 파일 검색, 코드 분석이 필요할 때 자동으로 여기에 위임된다.

**Plan** — Plan 모드에서 계획 전에 코드베이스를 조사하는 에이전트. 읽기 전용.

**General-purpose** — 탐색과 수정이 모두 필요한 복잡한 작업.

직접 Subagent를 만들 수도 있다. `.claude/agents/` 폴더에 마크다운 파일을 하나 만들면 된다.

```markdown
---
name: code-reviewer
description: 코드 품질과 보안을 검토하는 전문가. 코드 변경 후 자동으로 사용하세요.
tools: Read, Grep, Glob
model: sonnet
---

당신은 시니어 코드 리뷰어입니다. 코드를 검토할 때:
1. git diff로 변경 사항을 먼저 확인하세요
2. 보안 취약점, 성능 문제, 가독성 순서로 피드백하세요
3. Critical / Warning / Suggestion으로 구분해서 알려주세요
```

이렇게 만들면 Claude가 코드를 수정할 때마다 자동으로 이 Subagent에 위임한다. 메인 대화는 깨끗하게 유지된다.

Subagent에서 특히 유용한 설정이 있다.

**모델 선택**: Subagent별로 다른 모델을 쓸 수 있다. 단순 탐색은 Haiku, 복잡한 판단은 Sonnet이나 Opus. 비용을 많이 아낄 수 있다.

**도구 제한**: `tools: Read, Grep, Glob`처럼 읽기 전용으로 제한하면, Subagent가 실수로 파일을 수정하는 일이 없다.

**메모리**: `memory` 필드를 설정하면 Subagent가 대화 간에 학습한 내용을 유지한다. 코드베이스 패턴, 반복되는 이슈 같은 것들을. 저장 범위에 따라 세 가지 옵션이 있다.

| 옵션 | 저장 위치 | 언제 쓰나 |
|---|---|---|
| `user` | `~/.claude/agent-memory/<이름>/` | 여러 프로젝트에 걸쳐 같은 Subagent를 쓸 때. 예: 모든 프로젝트에서 쓰는 코드 리뷰어 |
| `project` | `.claude/agent-memory/<이름>/` | 이 프로젝트에 특화된 지식을 팀과 공유할 때. git에 커밋되어 팀원 모두가 같은 메모리를 쓴다 |
| `local` | `.claude/agent-memory-local/<이름>/` | 프로젝트에 특화되어 있지만 git에는 올리고 싶지 않을 때. 개인 노트처럼 |

혼자 쓰는 범용 Subagent라면 `user`, 팀 프로젝트의 Subagent라면 `project`가 기본값으로 적당하다.

Subagent는 병렬로 여러 개를 동시에 띄울 수 있다. "auth, database, API 모듈을 각각 분석해줘"라고 하면 Claude가 세 개의 Subagent를 동시에 생성한다. 단, 각 Subagent의 결과가 메인 컨텍스트로 돌아오기 때문에 많이 띄울수록 메인 컨텍스트가 빠르게 찬다. 병렬 수를 제한하는 설정은 없다. 걱정된다면 프롬프트에서 직접 "최대 3개씩만 병렬로 처리해줘"라고 지시하는 게 현실적이다.

Subagent를 background로 돌릴 때는 권한 처리 방식이 달라진다.

foreground로 실행 중인 Subagent는 권한이 필요한 순간 프롬프트가 터미널로 올라온다. 사용자가 직접 승인하면 된다. background Subagent는 다르다. 권한이 필요한 도구 호출을 자동으로 거부한다. Subagent는 멈추지 않고 계속 실행되지만 해당 작업만 실패로 처리된다.

background Subagent가 권한 부족으로 실패했다면, 같은 작업을 foreground Subagent로 새로 시작해서 대화형으로 재시도해야 한다.

미리 권한을 부여해두는 방법도 있다. Subagent 정의에 `permissionMode`를 설정하거나, 부모 세션에서 이미 승인된 권한은 Subagent에 그대로 상속된다.

```markdown
---
name: file-writer
permissionMode: acceptEdits   # 파일 편집 자동 승인
---
```

마지막으로 중요한 제약이 있다. Subagent는 Agent View에 나타나지 않는다. background 세션과 달리 실행 중 상태를 엿보거나 중간에 개입할 수 없다. 부모 Agent만 결과를 받을 수 있다. 중간 개입이 필요한 작업이라면 Subagent 대신 background 세션으로 직접 돌리는 게 맞다.

그런데 Subagent를 여러 개 동시에 돌리기 시작하자 두 번째 문제가 터졌다.

## 4단계: Worktree — 파일이 충돌한다

Subagent 여러 개를 병렬로 돌리면 어떤 일이 생길까?

Agent A가 `src/auth.ts`를 수정하고 있다. 동시에 Agent B도 `src/auth.ts`를 수정한다. 나중에 저장한 쪽이 이긴다. 한 쪽 작업이 사라진다.

실제로 이런 일이 일어난다.

Git worktree는 원래 Git 기능이다. 같은 저장소를 여러 디렉토리에 동시에 체크아웃할 수 있다. 각 체크아웃은 자기 브랜치를 갖는다. 파일이 완전히 분리된다.

```
[Worktree 구조]

저장소
├── main (현재 작업 중)
├── .claude/worktrees/feature-auth (Agent A가 여기서 작업)
└── .claude/worktrees/bugfix-123  (Agent B가 여기서 작업)
```

`--worktree` 플래그로 Claude를 시작하면 자동으로 새 worktree를 만들고 거기서 시작한다.

```bash
# 터미널 1
claude --worktree feature-auth

# 터미널 2
claude --worktree bugfix-123
```

두 세션이 완전히 다른 파일 공간에서 일한다. 충돌 없이.

Subagent에도 적용할 수 있다. Subagent 정의에 `isolation: worktree`를 추가하면, 그 Subagent는 항상 자기 worktree에서 실행된다.

```markdown
---
name: feature-implementer
description: 새 기능을 구현하는 에이전트
isolation: worktree
---
```

`.env`나 `.env.local` 같은 gitignore된 파일도 자동으로 복사하고 싶다면 `.worktreeinclude` 파일을 만들면 된다.

```
.env
.env.local
config/secrets.json
```

그런데 이제 에이전트가 여러 개가 됐다. 각자 worktree에서 일하고 있다. 어떻게 다 보지?

## 5단계: Agent View — 한눈에 보고 싶다

여러 에이전트가 병렬로 일하고 있다. 터미널이 여러 개다. 각 에이전트가 어디까지 했는지 확인하려면 각 터미널을 열어봐야 한다.

이건 불편하다.

Claude Code는 `claude agents` 명령으로 Agent View를 열어준다. 백그라운드로 실행 중인 세션들을 한 화면에서 모니터링하고, 필요할 때만 개입할 수 있는 관제탑 같은 역할이다. 세션을 백그라운드로 보내려면 대화 안에서 `/bg`를 입력하면 된다.

```
[Agent View]

고정됨
  ✽ auth-refactor      Edit src/auth/TokenService.ts          2m

검토 준비 완료
  ∙ payment-module     github.com/project/pull/142        ●   1h

입력 필요
  ✻ test-fix           needs input: mock 어디서 가져와?         30s

작업 중
  ✽ api-cleanup        Grep src/**/*.ts                        5m

완료됨
  ✻ docs-update        result: README 업데이트 완료              20m
```

한 화면에서 백그라운드 세션들의 상태를 본다. 어느 게 일하고 있는지, 어느 게 막혔는지, 어느 게 끝났는지.

`Space`를 누르면 해당 세션의 최근 출력을 엿볼 수 있다. 전체 대화를 열지 않아도. 거기서 바로 답변도 할 수 있다.

PR을 열었으면 행 옆에 점이 생긴다. 노란색이면 리뷰 대기, 초록색이면 통과. 점이 초록이 되면 그 에이전트 작업이 끝난 거다.

Agent View를 쓰면 에이전트를 디스패치하는 방식이 바뀐다.

```bash
# 에이전트 뷰에서 바로 새 세션 디스패치
> auth 모듈 리팩터링하고 PR 올려줘
> payment 모듈 버그 조사해줘
> 테스트 커버리지 높여줘
```

프롬프트 하나 입력하면 새 세션이 시작된다. 다른 창으로 전환할 필요 없다. 전부 여기서 보인다.

흥미로운 점이 있다. 백그라운드 세션은 세션 ID로 식별되는데, 같은 ID로 같은 머신의 여러 터미널에서 동시에 `claude attach`하면 동일한 화면이 미러링된다. 입력도 출력도 모든 창에서 동기화된다. tmux와 비슷하다. 모니터 여러 대에서 동시에 확인하거나 터미널을 분할해서 보는 용도로 쓸 수 있다.

그런데 이 단계에서 새로운 질문이 생겼다. 에이전트들이 서로 대화할 수 없을까?

## 6단계: Agent Team — 에이전트들이 협업한다

지금까지의 구조를 정리해보면 이렇다.

- Subagent: 메인 에이전트가 보조 에이전트에게 위임. 보조는 메인에게만 보고.
- Agent View: 사람이 여러 독립 세션을 감시.

둘 다 에이전트 간 직접 소통이 없다. 항상 사람이나 메인 에이전트를 통해야 한다.

복잡한 작업을 생각해보자. 프론트엔드, 백엔드, 테스트를 동시에 바꿔야 하는 기능 개발. 세 에이전트가 각자 일하는데, 백엔드 API 스펙이 바뀌면 프론트엔드 에이전트가 알아야 한다. 테스트 에이전트도 알아야 한다.

지금 구조로는 사람이 중간에서 다 중계해야 한다.

Agent Team은 이걸 해결한다.

```
[Agent Team 구조]

          리더 (나와 대화)
         /      |       \
    Frontend  Backend  Testing
    에이전트   에이전트   에이전트
         \      |       /
          공유 작업 목록
          (서로 메시지 가능)
```

팀원들은 공유 작업 목록을 가진다. 작업이 생기면 하나씩 가져간다. 다 끝나면 리더에게 보고하거나, 다른 팀원에게 직접 메시지를 보낸다.

쓰는 방법은 간단하다. 환경 변수를 켜고 Claude에게 자연어로 말하면 된다.

```json
// settings.json
{
  "env": {
    "CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS": "1"
  }
}
```

```
나: PR #142를 세 가지 관점에서 동시에 검토해줘.
    보안 리뷰어, 성능 분석가, 테스트 커버리지 검토자로 팀을 구성해.
```

Claude가 팀을 만들고, 팀원들이 병렬로 리뷰를 진행하고, 서로 발견한 것을 공유하고, 리더가 종합한다.

Subagent와 Agent Team의 차이를 직접 보면 이렇다.

| | Subagent | Agent Team |
|---|---|---|
| 통신 | 메인에게만 보고 | 팀원끼리 직접 메시지 |
| 컨텍스트 | 자기 창에서 시작 | 자기 창에서 시작 |
| 조율 | 메인이 전부 관리 | 공유 작업 목록 + 자율 조율 |
| 비용 | 낮음 | 높음 (팀원마다 토큰) |
| 언제 써야 하나 | 결과만 필요한 집중된 작업 | 토론과 협업이 필요한 복잡한 작업 |

Agent Team이 특히 빛나는 상황이 있다.

**경쟁하는 가설 테스트**: 버그 원인이 불명확할 때 5명이 각각 다른 이론을 동시에 테스트하고 서로 반박한다. 마지막까지 살아남은 이론이 진짜 원인일 가능성이 높다.

**교차 계층 기능 개발**: 프론트엔드, 백엔드, DB, 테스트가 동시에 바뀌어야 할 때. 각 팀원이 자기 레이어를 담당하면서 API 스펙 같은 공유 계약을 공유 작업 목록으로 맞춰나간다.

**다각도 연구**: 새 라이브러리 도입을 검토할 때. 성능, 생태계, 마이그레이션 비용, 보안을 각자 조사하고 종합.

Agent Team이 항상 좋은 건 아니다. 토큰 비용이 선형으로 증가한다. 팀원 10명이면 단일 세션 대비 약 10배 토큰을 쓴다. 순차적 작업이나 단순한 작업에는 오버킬이다.

## 실전 선택 가이드 — 언제 뭘 쓰는가

모든 걸 팀으로 돌릴 필요는 없다. 상황에 따라 적절한 도구가 다르다.

### "나는 지금 뭘 써야 하나?"

**일반적인 코딩 작업** → 그냥 Claude와 대화하면 된다. Subagent가 필요하면 Claude가 알아서 Explore에 위임한다.

**컨텍스트가 너무 길어진다** → 커스텀 Subagent를 만들어라. 탐색 작업을 격리하고 요약만 받아라.

**같은 저장소에서 두 작업을 동시에** → `--worktree`로 각 작업을 격리하라. 파일 충돌을 막는다.

**독립적인 여러 작업을 감시하고 싶다** → Agent View(`claude agents`). 디스패치하고 한 화면에서 본다.

**여러 에이전트가 결과를 공유해야 한다** → Agent Team. 단, 토큰 비용이 크게 증가한다는 걸 감수해야 한다.

정리하면 이렇다.

```
단순한 작업
    ↓
혼자 Claude와 대화

컨텍스트 폭발
    ↓
Subagent로 격리

병렬 작업, 파일 충돌 우려
    ↓
Worktree로 분리

여러 독립 세션, 감시 필요
    ↓
Agent View로 통제

에이전트 간 소통, 협업 필요
    ↓
Agent Team (비용 감수)
```

### 실제로 이걸 조합하면

현실적인 개발 시나리오를 하나 그려보면 이렇다.

```
1. Agent View에서 세션 세 개 디스패치
   - "feature/payment 브랜치 PR 만들어줘"    → worktree 자동 생성
   - "스테이징 서버 에러 로그 분석해줘"       → worktree 자동 생성
   - "테스트 커버리지 리포트 만들어줘"        → worktree 자동 생성

2. 에러 로그 분석 세션에서 Subagent 생성
   - Explore Subagent: 로그 파일 100개 읽고 요약
   - 메인 세션: 요약 받아서 패턴 분석

3. PR 세션 완료 → 행에 초록 점 생성
   → 검토 후 머지

4. 복잡한 리팩터링이 필요하다면
   → Agent Team 활성화
   → Frontend / Backend / Test 팀원 세 명 생성
   → 각자 담당 레이어 작업, 공유 인터페이스는 작업 목록으로 조율
```

한 작업 안에서도 Subagent, Worktree, Agent View가 함께 쓰인다. 이 도구들은 서로 경쟁하지 않는다. 레이어가 다르다.

## 정리: 진화의 방향

돌아보면 패턴이 보인다.

처음에는 사람이 루프를 닫았다. 그게 불편해서 에이전트가 나왔다. 에이전트가 컨텍스트를 먹자 Subagent가 나왔다. 병렬로 돌리니 파일이 충돌해서 Worktree가 나왔다. 여러 세션을 보기 힘드니 Agent View가 나왔다. 에이전트들이 서로 대화해야 하니 Agent Team이 나왔다.

이 진화의 방향은 하나다. **사람의 개입을 최소화하는 방향으로.**

처음엔 내가 루프의 중심에 있었다. 지금은 목표를 주면 에이전트 팀이 알아서 계획하고, 협업하고, 조율한다. 나는 결과를 검토하고 방향을 잡는다.

아직 모든 게 완성된 건 아니다. Agent Team은 아직 실험적이다. 토큰 비용도 많이 든다. 세션 재개가 완벽하지 않다.

그래도 방향은 분명하다.

루프를 위임하는 것. 그게 에이전트를 쓴다는 것의 핵심이고, 앞으로 이 도구들이 계속 진화하는 이유다.
